# P6-06 — Contract 0.4.0: note body document and content operations

## Goal

The contract gains the note body as a versioned structured JSON editor document (blocks with
paragraphs/headings/lists and inline marks incl. links, plus the derived plain text for search), a
new note-content operation with its inverse and valid/invalid fixtures; the 0.4.0 bump updates
`board.contracts`, every schema `$id`, the root `contractVersion`, fixtures, regenerated TS/C++
codegen and `docs/contracts.md`.

**Why:** the note body is explicitly left to the editor stage by contract 0.3.0 ("the note body is
the editor document and is added in the editor stage"); the own editor (P6-07) and the L05 save path
need a contract-shaped document and a one-operation-with-inverse update before content code is
written.

**Satisfies:** D12

## Scope

- `packages/contracts/` note body schema: a versioned, XSS-safe editor document as **structured JSON**
  (no HTML strings), e.g. `{ version, blocks: [...] }` with block types paragraph/heading/list and
  inline marks bold/italic/code/link; **link hrefs validated** (scheme allow-list, no `javascript:`),
  documented size limits (payload bytes, block count, text length) so a note cannot be abused as a
  payload channel; the **derived `plainText`** for search stored next to the document and required to
  be consistent with it.
- `packages/contracts/` integration: add the optional `body` + `plainText` to the note object (the
  existing note schema and the `notes[]` of `board-content.schema.json`; absent = empty note keeps
  0.3.0 content valid); a new `note-body-payload.schema.json` (a payload with required fields in its
  own file keeps the bump minor per the contract procedure) and the operation type
  `updateNoteBody` (payload `{ noteId, body }`) with its **inverse** carrying the previous body;
  unknown/future block types and unknown fields are rejected.
- `packages/contracts/` fixtures: valid bodies (empty, paragraph, marks, list, link) and invalid
  ones (bad href scheme, unknown block, missing version, oversized content, inconsistent plainText)
  in the fixtures corpora; board-content fixtures carry a body; operation fixtures for
  `updateNoteBody` + inverse.
- `packages/contracts/` the 0.4.0 bump: `board.contracts[].version`, every schema `$id`, root
  `contractVersion`, regenerated TS **and** C++ identical, `contracts`/`codegen` green; docs cover
  body shape, limits, search text, operation and tag; `contract_followups` lists the dependants
  (engine, sdk, services/platform, services/auth).
- `.changes/P6-06-<short-name>.md` (area `contracts`, kind `minor`).

## Specifications

- Wire format: editor stores the structured JSON, the app derives `plainText` deterministically on
  save; search consumes `plainText`.
- XSS safety: no HTML strings; link hrefs use an explicit scheme allow-list; text has documented
  length limits.
- Backward compatibility: a note without `body` is valid (empty), 0.3.0 content stays valid; the
  bump is minor (optional fields, own payload file) — follow the procedure and `contracts.py`.
- `updateNoteBody` inverse stores only the previous body; the operation carries `boardId`/`actorId`.
- Codegen: regenerate TS + C++, commit, dependants still typecheck; no hand edits.
- Fixtures use the repository conventions; valid/invalid specimens for every rule; update gate
  specimens if they cover notes.

## Pitfalls

- An enum-only operation addition can be under-classified by `contracts.py`; the new payload file is
  the safe route — read the procedure before choosing the bump.
- Strict `additionalProperties: false` means every new nested field must be declared; the editor and
  the app must not invent fields.
- A `plainText` that disagrees with the body breaks search; define the derivation precisely and test
  it (whitespace, list/paragraph separators, link text).
- Board-content fixtures are used by engine/convergence tests — keep them valid and minimal.
- Do not let `codegen` leave `packages/contracts` dirty; run it via the gate after the final schema.
- German text in fixtures/docs is fine in fixtures data, but code/comments stay English.
