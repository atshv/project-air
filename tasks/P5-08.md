# P5-08 — load proof: 25 clients per board at p95 <= 150 ms and the stage report

## Goal

Prove the realtime load target: 25 clients per board at p95 <= 150 ms with no errors (`load` gate,
exclusive), document the thresholds in `docs/gates/load.md`, record the measurement and commit the
stage report and handoff.

**Why:** the stage exit gate `load` and the measured proof of the stage goal; this task closes
stage 6.

**Satisfies:** D11

## Scope

- `services/sync/` load harness: 25 concurrent Node clients of the SDK on one board, a deterministic
  operation generator (moves/edits across the board), a short warm-up, then a documented measurement
  window; per-operation latency is measured from the client send to the received `ack` (definition
  recorded), with p50/p95/p99, error count, throughput and a final convergence check (every client's
  document equals the service snapshot). The harness starts/stops only its own service process on the
  slot port and resets its slot data afterwards.
- `services/sync/` small, protocol-neutral fixes if the run exposes one (bounded per-connection
  queue, per-board serialization, missing indexes, batched broadcast) — no contract change and no
  behaviour change beyond what the protocol already promises.
- `docs/gates/load.md`: the exact command, thresholds (p95 <= 150 ms, error rate 0), client count
  (25/board), measurement window, warm-up, environment recording, exclusive-run rule, evidence paths
  and cleanup; `docs/quality.md` gets the real `load` row instead of the `[VERIFY: stage realtime]`
  placeholder.
- `docs/realtime.md`: the stage report and handoff — measured numbers, environment, what is proven
  (25 clients/board, restart durability, offline convergence, 10k rounds), and remaining limits
  (single service instance, no horizontal scaling yet, presence traffic and browser UI follow in the
  web-app stage, reference machine is the M2 proxy). `.changes/P5-08-<short-name>.md` (area `sync`,
  kind `minor`).

## Out of scope

- Horizontal scaling, clusters or production sizing, reference-hardware measurements belonging to
  hardening, web-app UI, presence UI, contract changes, new dependencies, tuning thresholds after the
  run.

## Specifications

- Exclusive: the board task declares `exclusive: ["load"]`; the run uses the slot port/database, and
  no other browser/DB gate runs concurrently.
- Measure p95 over a documented minimum number of operations (at least 5,000) after a warm-up; do
  not report a number from a cold start or a window with client startup noise.
- Latency definition: client send time to `ack` receive (documented), measured in one Node process
  with 25 SDK clients; record the process/CPU environment.
- Errors mean any reject/exception/timeout; a non-zero count fails the gate. Convergence is checked
  at the end and must be exact.
- Thresholds are documented before the run; the run never adjusts them. Results are not comparable
  across machines — record the environment.
- Cleanup: stop only the service the harness started, reset its slot rows, leave no process behind.
- No new dependency; contract 0.3.0 frozen; boundaries respected.

## Pitfalls

- A cold Chromium/Node/DB start inside the measurement window inflates p95 — warm up first.
- 25 clients in one process share the event loop; document that the client process is not the
  bottleneck (measure server-side ack timestamps too or record CPU headroom).
- A missing index on `(board_id, server_seq)` or the catch-up query can dominate latency; check the
  query plans if p95 misses.
- Broadcasting to all 25 clients per batch serializes large messages; coalesce per board if needed
  without changing the protocol.
- Leftover server/DB rows break the next gate; the harness must clean up and reset the slot data.
- Never tune the threshold to pass: if p95 misses, fix the cause or report blocked.
