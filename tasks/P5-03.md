# P5-03 — Sync service: WebSocket protocol, auth and durable update log

## Goal

`services/sync` serves the 0.3.0 WebSocket protocol per board: `hello`/`welcome` with session and
version, authorized `joinBoard`/`leaveBoard`, `operationBatch` applied to `BoardDoc` and persisted
before the `ack` (`serverSeq`), broadcast, `snapshot`/`resyncRequest`/`reject` — with the update-log
and snapshot migration.

**Why:** the sync service is the server source of truth of the realtime stage (AD-2); P5-04, P5-05
and P5-06 build on it.

**Satisfies:** D11

## Scope

- `services/sync/` scaffold following `services/platform`: `package.json` with the module-map scripts,
  `tsconfig`, typed env configuration (port/`DATABASE_URL` from `.polier-slot`), health endpoint,
  secret-free logs, graceful shutdown, pinned `pg` pool (only runtime dependency).
- `services/sync/` WebSocket transport: a minimal RFC 6455 server on `node:http` upgrade (handshake,
  masked frames, continuation, ping/pong/close, bounded size, no extensions) with codec and
  malformed/oversized-frame tests. No new dependency — the repo writes its own thin layers
  (`services/platform` has its own router); tests and the later SDK use Node's global `WebSocket`.
- `services/sync/` protocol handling for the 0.3.0 contract: `hello` → `welcome` (version, session
  validation via auth/platform HTTP), `joinBoard` → platform board-access check + snapshot +
  catch-up from `fromServerSeq`, `operationBatch` → validate → apply through `BoardDoc` → append the
  update with the next `serverSeq` in one transaction **before** the `ack` → broadcast,
  `leaveBoard`, `resyncRequest` (state vector), `reject` with contract codes; presence is a stub for
  P5-05.
- `infra/migrations/0006_sync_log.sql`: per-board log `sync_updates(board_id, server_seq, update,
  client_id, created_at)` (PK board+seq), `sync_snapshots(board_id, server_seq, state, created_at)`
  and catch-up indexes; startup loads the latest snapshot and replays the log (compaction is P5-06);
  no slot 0 access.
- `docs/realtime.md`: architecture, message flow, durability ordering (commit → ack → broadcast),
  authorization double-check, run instructions (slot env), limits and the P5-04…P5-08 hand-off;
  `.changes/P5-03-<short-name>.md` (area `sync`, kind `minor`).

## Out of scope

## Acceptance

A1 WHEN a client connects, THEN `hello` must come first, the session is validated and `welcome`
carries the negotiated version; `joinBoard` is authorized per board (a foreign or unauthorized board
is rejected with the contract error) and `resyncRequest` only follows `joinBoard`.
A2 WHEN an `operationBatch` arrives, THEN it is validated, applied to the board's `BoardDoc`,
persisted with the next `serverSeq` in one transaction before the `ack`, broadcast to the other
clients, and a reconnect from `fromServerSeq` receives exactly the missed updates.
A3 WHEN the task is done, THEN `board-check`, `boundaries`, `unit` and `db-migrate` exit 0 with
records, the migration creates the update-log/snapshot tables, `docs/realtime.md` documents the
protocol/durability/authorization/run, and the service starts on the slot port with the slot
database.

## Specifications

- Ports, database and bucket only from `.polier-slot` (`python3 $POLIER/tools/slot.py show`); never
  hardcode a port and never touch slot 0's data.
- Authorization twice (AD-5): the platform board-access check on join and the database access scoped
  to the board/workspace; a rejected join must not open a stream.
- Durability order: validate → apply → append with `serverSeq` in one transaction → commit → `ack` →
  broadcast; an ack before the commit is the data-loss bug this task prevents.
- `serverSeq` is monotonic per board and survives restarts (read the current maximum at start).
- Validate every inbound message against the contract schema; reject with a contract error code,
  never with an exception; bound frame size and per-connection queue.
- Service imports only `packages/contracts` and `packages/crdt` (`boundaries` gate); no secrets or
  session tokens in logs; the `pg` dependency is the only runtime one and stays pinned.
- Tests start their own server on the slot port, use their own slot database, and clean up; never
  stop processes they did not start.

## Pitfalls

- A `pg` transaction that appends the update but acknowledges before `COMMIT` loses the change on a
  crash; the ack must follow the commit.
- Two batches can race on the same board: serialize per board (one writer per board) and allocate
  `serverSeq` inside the transaction/row lock.
- Node's global `WebSocket` is a client only; do not assume a server API exists — write the codec or
  ask before adding a dependency.
- Fragmented/unmasked frames are attack surface: enforce masking, length limits, ping/pong, close.
- A fresh board has no snapshot row; `serverSeq` starts at 1 (P5-01) — test the empty-board join.
- Validate the session once per connection/join, not per message; document the refresh rule.
