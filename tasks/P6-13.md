# P6-13 — Block content and zone rename in the CRDT, sync and SDK

## Goal

`packages/crdt`, `services/sync` and `packages/sdk` accept contract 0.5.0: `updateBlockContent` and
`updateZone` apply to the board document with their inverses, converge between clients, survive a
sync restart and are exposed by the SDK board-sync client like every other operation.

**Why:** owner decision 2026-10-29 (close the stage-7 gaps first). The app can only store a
checklist point or a zone name through the one L05 save path once the shared document and the sync
service know the 0.5.0 operations.

**Satisfies:** D12

## Scope

- `packages/crdt/` BoardDoc: block `content` in the Yjs document (per-item maps keyed by item id,
  so two clients editing different points of one checklist both keep their change), the two new
  operations and their inverses, `snapshot()` emits contract-valid 0.5.0 content; both adapters
  (Yjs and the fake second adapter) pass the conformance suite including the new operations.
- `services/sync/` protocol/types: version negotiation accepts 0.5.0, operation validation lets the
  new types through, operations-log replay and snapshot compaction keep block content and zone
  titles; restart fixtures cover both.
- `packages/sdk/` types and the board-sync client: the operations go through the existing
  autosave/flush/offline-queue path; own-ops undo/redo covers them.
- Tests: CRDT conformance rounds with the new operations (concurrent point edits, concurrent rename
  vs member move), sync integration + restart test, SDK unit tests.
- `.changes/P6-13-<short-name>.md` (area `realtime`, kind `minor`).

## Out of scope

- Engine and app wiring (P6-14, P6-21); auto-compaction scheduler; RLS on sync tables.

## Acceptance

A1 WHEN two clients edit different items of the same checklist or rename a zone while another moves
a member, THEN both converge to the same contract-valid content with no lost item, in the
conformance suite for both adapters.
A2 WHEN the sync service restarts after acknowledging `updateBlockContent`/`updateZone`, THEN a
fresh join receives the content and title unchanged.
A3 WHEN the task is done, THEN `unit`, `typecheck`, `crdt-convergence`, `board-check` and
`boundaries` exit 0 with records and the change entry exists.

## Specifications

- Follow how `updateNoteBody` (contract 0.4.0) was adopted in each package: same layering, same
  test style.
- One operation = one CRDT transaction; the inverse restores exactly the previous content/title.
- Item order inside a list is part of the content; concurrent inserts keep both items in a
  deterministic order.

## Pitfalls

- Replacing the whole `content` object on every edit loses concurrent point edits; merge per item.
- The sync service rejects unknown operation types; forgetting the validator makes the app look
  saved locally but never acknowledged.
- Restart fixtures must include a compacted snapshot, not only the log.
