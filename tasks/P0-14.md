# P0-14 — Change entries and changelog gate

## Goal

Every code change carries a `.changes/` entry, the `changelog-entry` gate rejects code changes
without one, `CHANGELOG.md` starts at `0.0.1`, and the version scheme is `0.0.1` plus letter
entries (Q10, owner 2026-10-25).

**Why:** parallel tasks must never collide on `CHANGELOG.md`; the release stage (remote) collects
the entries into a release section.

**Satisfies:** D5

## Scope

- `.changes/`: `README.md` (rules, areas, kind values, naming, `no-changelog` owner exception),
  a template, one entry per done foundation task (`P0-03`, `P0-04`, `P0-06`, `P0-07`, `P0-10`,
  `P0-11`, `P0-12`, `P0-13`, `P0-18`, `P0-19`) and the entry for this task.
  File name: `<task-id>-<short-name>.md`; content: area, kind (`patch`/`minor`/`major`), one-line
  English summary. No release sections here.
- `tools/release/`: dependency-free Node.js ESM package (Node builtins only):
  - `change.mjs`: CLI `node tools/release/change.mjs --task <ID> --area <area> --kind <kind> "<summary>"`
    (also usable as `pnpm change -- <area> <kind> "<summary>"` through the root `change` script)
    writes `.changes/<ID>-<slug>.md`, refuses unknown areas/kinds and overwrites only with `--force`.
  - `check-changes.mjs`: CLI `node tools/release/check-changes.mjs [--base main] [--task ID]`; it
    inspects changed files (committed against `--base` plus the working tree) and fails when code
    under `apps/`, `packages/`, `services/`, `tools/`, `infra/` or the root manifests changed without
    a matching `.changes/<ID>-*.md`; docs/board/STATUS/reviews/`tasks/` are not code. Exit 0 clean,
    1 missing entry, 2 usage/configuration. Support the documented owner exception label
    `no-changelog` as a `--no-changelog` flag with a required reason.
  - Unit tests with temporary git repositories/fixtures (code change without entry → fail; with
    entry → pass; docs-only → pass; `--no-changelog` with reason → pass; writer validation).
  - `tools/release/package.json` with `test`; README/ARCHITECTURE update.
- `CHANGELOG.md`: `# Changelog` with `## 0.0.1 – unreleased` and the rule that agents never edit
  it directly; entries are collected from `.changes/` at release. The letter entries
  (`0.0.1a`, `0.0.1b`, …) are for unmerged intermediate steps and are added by the release tooling
  in the remote phase; `package.json` does not change for them.
- Root `package.json`: add `"change": "node tools/release/change.mjs"` and set the version to
  `0.0.1` (start of the Q10 scheme); no dependencies.
- Update `AGENTS.md` with the one-line `change` rule (≤ 400 words; trim wording if needed) and
  `docs/module-map.md` with the `tools/release` commands.

## Out of scope

- Release version bumping, tags, release PRs, CI release workflow (remote stage, P0-15/P0-17),
  CHANGELOG editing by agents, new dependencies.

## Acceptance

A1 WHEN a code task changes code and has no `.changes/<ID>-*.md`, THEN `check-changes` exits 1 and
names the missing entry; with an entry it exits 0; docs-only changes and a `--no-changelog`
exception with reason also exit 0.
A2 WHEN `.changes/` is read, THEN every done foundation task has exactly one entry with area, kind
and English summary, and this task's own entry exists.
A3 WHEN `CHANGELOG.md` is read, THEN it starts with `# Changelog` and `## 0.0.1 – unreleased`; the
root manifest version is `0.0.1`; `pnpm change` writes a valid entry and refuses bad input.
A4 WHEN the `changelog-entry` and `unit` gates run through `gate.py`, THEN both exit 0 and records
are committed; `python3 $POLIER/tools/check.py .` exits 0 (run before `pnpm install`).

## Context pack

**Read exactly:**

- `ARCHITECTURE.md` (AD-10), `AGENTS.md`, `STATUS.md`, `docs/module-map.md`, `docs/quality.md`
- `docs/releasing.md`
- `docs/owner/canvas-suite-blueprint.md` sections 22.1 and 22.3 (version scheme, changelog rules)
- `package.json`, `board.json` (done tasks and Q10 answer)

**Do not read:** other briefs, `reference/`, other packages.

**Budget:** ≤ 20k tokens input.

## Specifications

- **Areas:** `web`, `engine`, `sync`, `platform`, `auth`, `media`, `ai`, `contracts`, `infra`,
  `tooling`; kinds: `patch`, `minor`, `major` (default `patch`).
- **Entry format:** short markdown with `area:`, `kind:`, a one-line English summary and the task
  id in the file name; no release headers, no dates.
- **Change helper:** task id from `--task` or branch name `task/<ID>`; short name slug from the
  summary; refuse an existing file unless `--force`; deterministic output.
- **Gate command:** `node tools/release/check-changes.mjs --task <ID> --base main`; report the exact
  command for `docs/quality.md`.
- **Language:** entries and tool output English; no German.
- **No dependencies; no changes outside the scope; the tool never edits `CHANGELOG.md`.**

## Pitfalls

- The gate runs before a commit; inspect the working tree as well as `--base...HEAD`.
- `.changes/` entries are per task, not per file; one entry per task is enough.
- Do not add CI workflow files (P0-08, remote stage).
- `check.py` scans `node_modules/`; run `board-check` before any install.
- Keep the root `package.json` version change to `0.0.1` only; no dependency changes.

## Edge cases

- Branch is not `task/<ID>` and `--task` is missing → exit 2 with a clear message.
- A path matches both a code prefix and an ignore prefix (e.g. `tools/design-check/test/fixtures/`)
  → still code for this gate; the task must carry an entry.
- Owner exception: `--no-changelog "reason"` passes only with a non-empty reason; document that it
  is owner-only.

## Gates

1. `changelog-entry`: `node tools/release/check-changes.mjs --task P0-14 --base main` → exit 0.
2. `unit`: `pnpm --filter ./tools/release test` → exit 0.
3. `board-check`: `python3 $POLIER/tools/check.py .` → exit 0 (before `pnpm install`).

## Limits

- **Scope:** only `.changes/`, `tools/release/`, `CHANGELOG.md`, `package.json`, `docs/module-map.md`, `AGENTS.md`; gate records under reviews/evidence are always allowed.
- **Stop:** 3 rounds; when blocked, `status: blocked` + reason.
