# P2-05 — Engine architecture ADR, module docs and stage showcase

## Goal

ADR-0006 records the engine architecture with the measured evidence, `docs/engine.md` documents the
C++ module list and canvas-catalogue mapping, and desktop/mobile showcase screenshots of the
playground are committed.

**Why:** the engine-spike exit criterion needs the measured report plus the ADR; engine-core builds
on the documented module map and the measured baseline.

**Satisfies:** D8

## Scope

- `docs/adr/ADR-0006-engine-architecture.md`: context (50,000 rectangles at 60 fps, C++20 → WASM,
  contract generated header, ui-kit tokens, no network in the engine), decision (C++20 core with
  `doc`/`camera`/`spatial`/`render` command buffer; WebGL2 instanced rendering in the spike, WebGPU
  behind the same command interface in engine-core; Emscripten build with pinned versions; thin TS
  bridge; no per-object JS calls), consequences (positive/negative/binds/prevents), alternatives
  (TypeScript + Canvas2D, WebGPU-only, Rust/WASM). Reference the measured numbers and the size
  budget; add the ADR to `board.json` decisions via the lead (do not edit `board.json` yourself).
- `docs/engine.md`: module list with one line each (purpose, inputs, outputs, imports), the
  canonical-coordinate grid (16 px world grid, fractional z), the command-buffer instance layout,
  the build commands (native/WASM/size/perf), and the mapping to the canvas acceptance catalogue
  (L01 performance target and the engine-owned entries) per `docs/canvas-acceptance.md`.
- Stage showcase: serve the playground from the worktree's slot port (`.polier-slot`, never
  hard-code), capture `reviews/evidence/P2-05-desktop.png` (1440×900), `P2-05-mobile.png`
  (390×844) and `P2-05-playground.log` with the exact serve/curl/screenshot commands, HTTP
  statuses, screenshot sizes and the 50,000-rectangle/fps evidence; start and stop only your own
  server.
- `docs/quality.md`: only if a link/threshold needs correcting; no engine code changes.
- No `.changes` entry (docs and evidence only, no code change).

## Out of scope

- Engine code, renderer, bridge or playground changes; new gates or dependencies; re-running the
  perf baseline (its record is referenced, not replaced); `board.json`/`STATUS.md` edits (lead).

## Acceptance

A1 WHEN ADR-0006 is read, THEN it is a complete ADR in the project style that decides the engine
architecture and cites the measured perf/size evidence.
A2 WHEN `docs/engine.md` is read, THEN every engine module, the instance layout, the build commands
and the canvas-catalogue mapping are documented and consistent with the code.
A3 WHEN the showcase evidence is read, THEN desktop (1440×900) and mobile (390×844) screenshots plus
a log with the exact commands and HTTP statuses are committed under `reviews/evidence/`.
A4 WHEN `board-check` and `design-check` run, THEN they exit 0 with records committed.

## Specifications

- ADR shape: Date, Status accepted, Supersedes `–`, Context, Decision, Consequences
  (positive/negative/binds/prevents), Alternatives; English, 300–600 words.
- Numbers only from the committed P2-04 evidence/report; never re-estimate silently. If the report
  marks a number as proxy (M2 dev machine vs M1 reference), the ADR states the same limitation.
- `docs/engine.md` is the module reference for engine-core; keep it factual and short (≤ 800 words),
  with a small table of modules and a short "what the spike does not prove yet" section.
- Screenshots: the playground page with the 50,000-rectangle demo, fps counter visible; no raw
  colours or new UI in this task (it only documents what exists). If the page needs a scroll to show
  the canvas, capture the viewport that shows it.
- The demo cadence rule applies: the stage showcase supplements the gates, it does not replace them.

## Pitfalls

- Do not edit `board.json` to add the ADR decision; report the file path to the lead, who records it.
- Do not restate the blueprint as architecture; decide and cite evidence.
- Do not commit screenshots from the wrong port/worktree or from a stale build; serve the current
  worktree artifacts.
- `check.py` scans `node_modules/`; run board-check before any `pnpm` command if the worktree has an
  install.
- Keep the ADR and `docs/engine.md` English; German only in quoted owner text with `ss`.

## Edge cases

- The perf report marks the local hardware deviation → the ADR and the stage handoff must repeat the
  limitation, not hide it.
- The playground cannot render WebGL in the screenshot browser → capture with the software renderer
  and say so in the log (screenshots are not perf evidence).
- 50,000 rectangles and the fps counter must be visible; if the counter is off-screen at 390 px,
  choose a crop/viewport that shows the demo and say it in the log.
