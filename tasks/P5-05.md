# P5-05 — Presence: cursors, selection, name and colour

## Goal

Presence (cursor, selection, name, colour) travels over the sync protocol from `services/sync` to
the SDK: throttled, ephemeral (never persisted), cleaned up on disconnect and joinable per board,
with tests for throttling, cleanup and no interference with operation traffic.

**Why:** `services/sync`'s architecture promises presence; collaboration needs it and it must stay
ephemeral, not become board state.

**Satisfies:** D11

## Scope

- `services/sync/` presence hub: receive the contract `presence` message from a joined connection,
  validate it against the contract, rate-limit/throttle per connection (documented maximum rate and
  payload size), stamp the sender identity from the validated session (a client cannot spoof name or
  colour), broadcast to the other connections of the same board only, and never write presence to
  PostgreSQL. On `leaveBoard`, disconnect, protocol error or shutdown, send a final remove/leave
  presence to the room and drop the state; on join, send the current participants to the newcomer.
- `services/sync/` integration with the existing protocol loop from P5-03 (one message path, no
  second socket): presence must not delay or drop `operationBatch` processing; a flood of presence is
  dropped/coalesced with the same connection budget.
- `packages/sdk/` presence client: throttle outbound cursor/selection updates (for example to one per
  animation frame or a documented interval), expose a subscription with the remote participants
  (`{ participantId, name, colour, cursor, selection }`), clear on leave/reconnect and on board
  switch; the SDK never persists presence and never sends it while disconnected; local throttling
  uses an injected clock in tests.
- `docs/realtime.md`: presence message flow, throttling limits, ephemerality, per-board isolation and
  the SDK API; `.changes/P5-05-<short-name>.md` (area `sync`, kind `minor`).

## Out of scope

- Rendering cursors/avatars or UI state (web-app stage), persistence, history/replay, voice/video,
  contract changes beyond using the existing `presence` payload (if a field is genuinely missing,
  record an open question instead of widening this task), authentication changes, new dependencies.

## Acceptance

A1 WHEN two clients are joined to one board, THEN each receives the other's throttled presence
(cursor, selection, name from the session, colour) and none after leave, disconnect or shutdown, and
nothing is written to PostgreSQL.
A2 WHEN a client sends presence too fast or too large, THEN the service coalesces/drops the excess
without affecting operation traffic (an `operationBatch` still acks within the normal budget), tests
cover throttle, cleanup and per-board isolation, and `board-check`, `boundaries` and `unit` pass with
records.

## Specifications

- Presence is the existing contract `presence` message; validate it, never invent a second message
  type; identity (name, colour, participant id) is server-derived from the session.
- Ephemerality: no presence row in PostgreSQL, no persistence in the SDK, nothing replayed after
  reconnect beyond the fresh participant list.
- Throttling/coalescing: a documented per-connection budget; excess is dropped silently (no error
  storm) and operation batches keep their priority.
- Isolation: presence goes only to connections of the same board; leaving or a closed socket removes
  the participant and sends the leave to the room.
- Deterministic tests: fake connections and an injected clock; no real timers, no sleeps.
- Imports per `boundaries`: `services/sync` uses contracts+crdt; the SDK uses contracts+crdt; no new
  dependency.

## Pitfalls

- Storing presence in a table or replaying it on join turns ephemeral state into board data — do not.
- A presence flood that shares the operation queue can starve acks; throttle/coalesce before the
  broadcast and test that an `operationBatch` still acks normally.
- Colour/name spoofing: overwrite them from the session; test that a client-sent name is ignored.
- Cleanup on abrupt disconnect, `leaveBoard`, rejected join and graceful shutdown must all be tested.
- A reconnect can duplicate the participant list; clear local presence first and re-send the fresh
  list once.
