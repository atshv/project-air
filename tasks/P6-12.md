# P6-12 — Contract 0.5.0: block content and zone rename

## Goal

The contract gains the content of checklist, columns and table blocks and a zone rename operation:
`Block.content` (typed per block type, size-limited), the operations `updateBlockContent` and
`updateZone` with their inverses, valid/invalid fixtures, the 0.5.0 bump and regenerated TS/C++.

**Why:** owner decision 2026-10-29 ("close the gaps first"): the web app must behave like the live
demo before the value stage. Blocks today carry geometry only, so L18 inline comfort cannot store a
checklist point, and P4-30 renames a zone through a delete + create group, which is fragile under
realtime. Both need a contract shape before engine, CRDT and app code are written.

**Satisfies:** D12

## Scope

- `packages/contracts/` block content: optional `content` on `Block`, discriminated by `type`:
  - `checklist`: `{ items: [{ id, text, done }] }`
  - `columns`: `{ columns: [{ id, title, items: [{ id, text }] }] }`
  - `table`: `{ columns: [{ id, title }], rows: [{ id, cells: { <columnId>: text } }] }`
  - `palette` / `timeline`: no content yet (absent stays valid; a later bump adds them).
  Ids are UUIDv7 strings; documented limits (items per block, text length, total payload bytes);
  plain text only (no HTML, no marks).
- `packages/contracts/` operations: `updateBlockContent` (payload `{ blockId, content }`, inverse
  carries the previous content) and `updateZone` (payload `{ zoneId, title }`, trimmed, 1…40
  characters, inverse carries the previous title). Payloads with required fields live in their own
  schema files so the bump stays minor.
- `packages/contracts/` fixtures: valid content per supported type, empty lists, the rename; invalid
  content for a mismatched type, unknown fields, oversize text/lists, missing ids, empty or 41-char
  titles; board-content fixtures carry block content.
- The 0.5.0 bump: `board.contracts[].version`, every schema `$id`, root `contractVersion`,
  regenerated TS **and** C++ identical, `docs/contracts.md` (shapes, limits, operations, the
  `contract_followups`: crdt, sync, engine, sdk, apps/web).
- `.changes/P6-12-<short-name>.md` (area `contracts`, kind `minor`).

## Out of scope

- Adopting the operations in CRDT, sync, engine or the app (P6-13, P6-14, P6-21); palette/timeline
  content; images and edges.

## Acceptance

A1 WHEN the fixtures run, THEN every new valid fixture passes and every invalid one fails with the
expected keyword in TS and C++ identically, and 0.4.0 board content without block content stays
valid.
A2 WHEN `updateBlockContent` or `updateZone` is validated, THEN payload and inverse are required and
round-trip (apply + inverse = previous state) in the contract tests.
A3 WHEN the task is done, THEN `contracts`, `codegen`, `unit`, `board-check` and `boundaries` exit
0 with records, `docs/contracts.md` documents 0.5.0 and the change entry exists.

## Specifications

- Follow the P6-06 bump pattern exactly (schema files, `$id`s, codegen, parity).
- `content` must match `type`; a checklist content on a table block is invalid.
- Limits are numbers in the schema and in the docs, never only in prose.
- Titles: whitespace collapsed by the client; the schema checks 1…40 characters after trim.

## Pitfalls

- The engine wasm asserts the contract version (P6-10 found this); list it in `contract_followups`.
- C++ codegen must handle the discriminated content; check the generated header compiles.
- Do not make `content` required: existing blocks would become invalid.
