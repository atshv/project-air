# P5-06 — Durability and reconnect: restart, catch-up and snapshot compaction

## Goal

An acknowledged change survives a service restart, catch-up from a state vector/`fromServerSeq`
returns exactly the missed updates, `serverSeq` is continuous across a restart, and the update log
compacts into snapshots without losing acknowledged operations — proven with a slot-database restart
harness.

**Why:** the stage exit criterion "restart loses no acknowledged change"; P5-07 and P5-08 rely on a
durable log and an exact catch-up.

**Satisfies:** D11

## Scope

- `services/sync/` recovery: on start load the latest snapshot and replay the update log after its
  `serverSeq`; the per-board `serverSeq` continues monotonically across restarts (read the current
  maximum in the same transaction that allocates the next one); an empty board starts at 1.
- `services/sync/` graceful shutdown: stop accepting new connections/messages, finish in-flight
  transactions, close sockets with the contract close code, flush presence (P5-05) and never `ack`
  after shutdown started.
- `services/sync/` catch-up: after a stop/reconnect, `resyncRequest` with the client state vector or
  `fromServerSeq` returns exactly the missed encoded updates (no gap, no duplicate, ordered by
  `serverSeq`); a client installing snapshot+updates ends in the same state as the service.
- `services/sync/` snapshot compaction: a documented policy (log length and/or size threshold)
  writes an atomic snapshot of the board document at a `serverSeq`, then prunes only updates that the
  snapshot covers; an acknowledged update is never pruned before it is contained in a committed
  snapshot; database growth stays bounded; compaction runs without blocking operation batches
  (bounded work per board).
- `infra/migrations/` only if an index/column is needed for the catch-up or compaction queries (a
  new migration then).
- Restart harness and evidence: a slot-database test that spawns the service, applies N operations
  with acks, terminates it (SIGTERM), restarts it, reconnects and asserts every acknowledged operation
  is present, `serverSeq` continues, and the catch-up is exact; a compaction test that produces the
  same state as an uncompacted run. Records under `reviews/evidence/` (JSON summary + gate logs).
- `docs/realtime.md`: recovery, catch-up and compaction policy; `.changes/P5-06-<short-name>.md`
  (area `sync`, kind `minor`).

## Out of scope

- Load and performance proof (P5-08), convergence rounds (P5-07), presence (P5-05), horizontal
  scaling, contract changes, new dependencies, changes to the P5-03 protocol messages.

## Acceptance

A1 WHEN the service acknowledged N operations and is restarted, THEN all N survive, `serverSeq`
continues monotonically and no acknowledged operation is lost; the restart harness record proves it.
A2 WHEN a client reconnects with `fromServerSeq` or a state vector after a stop, THEN it receives
exactly the missed updates (no gaps, no duplicates, in order) and its document equals the service's
state.
A3 WHEN the log compacts, THEN snapshot plus remaining log reproduce the same board state, an
acknowledged operation is never pruned before a committed snapshot contains it, and `board-check`,
`boundaries`, `unit` and `db-migrate` exit 0 with records; `docs/realtime.md` documents recovery and
compaction.

## Specifications

- Ports, database and bucket only from `.polier-slot`; the harness starts and stops only its own
  service process and cleans its slot data.
- Durability invariant: commit → ack; the restart test must prove the ack means durable (kill after
  ack, not before).
- `serverSeq` allocation and log append are one transaction per board; catch-up is ordered and
  inclusive/exclusive as documented (from `fromServerSeq` exclusive, i.e. the next expected update).
- Compaction is atomic per board: write the snapshot at `S`, then prune updates `<= S`; a crash
  between the two leaves either the old state or the new one, never a lost acknowledged update.
- The client-side catch-up uses the same `BoardDoc` interface as the service (no second encoding).
- Tests use the slot database, are deterministic, and leave no process or row behind; gate records
  under `reviews/evidence/`.

## Pitfalls

- An ack sent before `COMMIT` loses data on a crash — the restart test must kill after an ack.
- A snapshot at `serverSeq` S must install before updates `> S`; applying updates before the snapshot
  mixes states.
- Pruning by time or blindly by count can drop an update that no snapshot covers — prune only
  `<= snapshot.serverSeq`.
- A crash between snapshot write and prune must not lose acknowledged updates; test the order.
- Catch-up duplicates: the boundary `fromServerSeq` is easy to get wrong (off-by-one) — test the
  empty case, a one-update gap and a large gap.
- A restart while clients are connected must close them with a retryable code, not silently.
