# P1-06 — Contract documentation, ADR and 0.1.0 metadata

> **Size:** target 500–800 words. Docs-only task: the contract itself is finished by P1-04/P1-05.

## Goal

The contract is documented and discoverable: `docs/contracts.md` explains its zones, fixtures,
codegen, version rules and change procedure, and `ADR-0005` records why the contract is
schema-first and versioned; the machine-readable `board.contracts[]` metadata (lead-owned) is
checked by the `contracts` gate. The stage closes at contract version `0.1.0`.

**Why:** engine (C++), backend and web build on this contract next; without one documented,
versioned entry point every later stage invents its own copy (AD-3).

**Satisfies:** D7

## Scope

- `docs/contracts.md` (new): the single human entry point for contract `0.1.0`:
  - purpose, binding rules (AD-1, AD-2, AD-3, AD-4, AD-8 for `messageKey`), consumer model;
  - the three schema families and their 16 schema files: board-content (10 top-level schemas),
    sync protocol (`schemas/sync/`), API resources/errors (`schemas/api/`);
  - fixture corpora: the 77-fixture parity corpus under `fixtures/` (32 valid / 45 invalid),
    `fixtures-sync/`, `fixtures-api/` and `fixtures-gate/` (the two Polier gate specimens and
    why they exist);
  - codegen: `codegen.mjs` → `generated/types.ts` + `generated/contract.h`, determinism and the
    TS/C++ parity harness;
  - version rules and bump table (major = removed/renamed field or changed meaning or new required
    field; minor = new optional field or new operation/message; patch = docs/fixtures only) and
    the change procedure (schema + fixture + codegen + every dependant + versions in the same
    task; no renames, deprecate first);
  - `board.contracts[]` entry and how to change it; `dependants` is empty today and is filled by
    the task that first imports the contract (engine-spike, backend-core, …);
  - the `0.1.0` tag policy: the version is recorded in `board.contracts[]`, every schema `$id`
    and the root `contractVersion`; the annotated git tag/release happens in the remote phase
    through the owner's release flow (ADR-0002, ADR-0003). Agents never tag.
  - an **open points before realtime/SDK** section from the P1-04/P1-05 reviews: GET `requestId`
    transport, connection-scoped contractVersion vs blueprint §5.1, `serverSeq` bootstrap (0/1),
    `hello`-first and `snapshot:<boardId>:<serverSeq>` rules.
- `docs/adr/ADR-0005-contract.md` (new): "Contract and versions" — context, decision (JSON
  Schema 2020-12 source of truth, valid+invalid fixtures, deterministic TS/C++ codegen with a
  parity harness, SemVer rules), consequences (positive/negative/binds/prevents), alternatives
  (hand-written types; Protobuf/OpenAPI; schema without fixtures; tag now). ADR shape, status
  `accepted`, date 2026-10-25.
- `board.contracts[]` is filled by the **lead** before the task starts (path, version, schema
  files, `fixtures_dir`, empty dependants); verify it with the `contracts` gate and describe it
  in `docs/contracts.md`. Do not edit `board.json`.
- Do **not** change any file under `packages/contracts/`: the `contracts` gate compares contract
  files against `main` and a change without a version bump fails (the stage must close at
  `0.1.0`, so no bump is allowed here). Both schema families, all fixtures and the gate specimens
  already exist.
- No `.changes` entry: docs/board/status work does not need one.

## Out of scope

- Changing schemas, fixtures, codegen or generated files; runtime validation; sync/API
  implementation; the preview overview (P1-07); new dependencies.

## Acceptance

A1 WHEN `docs/contracts.md` is read, THEN it names the contract version, every schema family and
schema file, every fixture corpus, the codegen outputs, the version rules, the change procedure,
the `board.contracts[]` entry and the tag policy.
A2 WHEN `docs/adr/ADR-0005-contract.md` is read, THEN it is a complete ADR (context, decision,
consequences, alternatives) that matches the implemented contract and the Polier version rules.
A3 WHEN the `contracts`, `unit` and `board-check` gates run through `gate.py`, THEN all exit 0
with records committed; `python3 $POLIER/tools/contracts.py check` validates the lead's
`board.contracts[]` entry, its schema files and `fixtures-gate/valid+invalid`.
A4 WHEN the diff is inspected, THEN it contains only `docs/contracts.md`,
`docs/adr/ADR-0005-contract.md` and the gate records — no file under `packages/contracts/`, and no
new dependency.
