# P0-22 — Version and last change in the preview masthead

## Goal

The design preview shows the current changelog version and the latest change entry in a small
meta line at the top (under the masthead), so a viewer immediately sees which build and which
change the preview represents.

**Why:** the owner wants the preview to identify itself: changelog version plus last change.

**Satisfies:** D3

## Scope

- `apps/web/preview/index.html`: add a meta line under the intro paragraph, e.g.
  `Version 0.0.1 · unreleased · Last change: P0-21 — Match the demo connection to the design
  system`, with stable elements the page can update later.
- `apps/web/preview/preview.css`: token-only styling for the meta line (small, `--muted`,
  separators via `--border`, 4-px spacing); no raw colours.
- `apps/web/preview/README.md`: document where the two values come from
  (`CHANGELOG.md` first version heading and the latest `.changes/<task>-<name>.md` summary) and the
  rule that they are updated in the same task as every preview change (demo cadence).
- Refresh `reviews/evidence/P0-22-demo.png` (1440×900) showing the meta line at the top; keep
  `P0-21-demo.png` untouched.
- `.changes/P0-22-preview-version.md` (area `web`, kind `patch`, one English line).

Keep it static and dependency-free: no build step, no fetch at runtime; the values are written
from the named sources by the task and kept in sync by the same-task rule.

## Out of scope

- Runtime parsing of CHANGELOG/`.changes`, a release tool for preview metadata, version bumping,
  CI, engine or data.
- Changes outside `apps/web/preview/` and `.changes/`.

## Acceptance

A1 WHEN the preview is opened, THEN a meta line under the masthead shows the current changelog
version (`0.0.1`, status `unreleased`) and the latest `.changes` entry (task id and summary).
A2 WHEN the preview README is read, THEN it names both sources and the same-task update rule.
A3 WHEN `board-check`, `design-check` and `changelog-entry` gates run, THEN all exit 0 with records
committed; the refreshed screenshot shows the meta line; `check.py` exits 0 (before
`pnpm install`).

## Context pack

**Read exactly:**

- `apps/web/preview/` (all files), `CHANGELOG.md`, `.changes/` (README and entries),
  `docs/quality.md` (demo cadence), `AGENTS.md`, `packages/ui-kit/tokens.css`,
  `docs/design-rules.md` §2/§4
- `.changes/README.md`, `docs/module-map.md` (change commands)

**Do not read:** other briefs, `reference/`, other packages.

**Budget:** ≤ 15k tokens input.

## Specifications

- **Version source:** `CHANGELOG.md` first `##` heading (`0.0.1 – unreleased`) and/or root
  `package.json` version; they currently agree. Use `CHANGELOG.md` as the display source and note
  the package version.
- **Last change:** highest task id under `.changes/` (`P0-21-demo-connection.md` today), with its
  one-line summary; render as `P0-21 — <summary>`.
- **Styling:** a single line or two short spans separated by `·`, `--muted`, `--text-12`,
  `--space-8`; token-only; responsive (wraps on 390 px, no horizontal overflow).
- **No JavaScript requirement:** the values are static in the HTML for this task.
- **Screenshot:** serve on the slot web port, headless Chromium, 1440×900, real page.

## Pitfalls

- Do not invent a newer version than `CHANGELOG.md`/`package.json` show.
- Do not drop the existing demo or renumber sections unnecessarily.
- Do not use raw colours for the separators or the muted text.
- Keep the page offline-capable: no external fonts or CDNs.

## Edge cases

- `.changes/` with several entries for the same task → use the newest file and document the pick
  rule in the README.
- A version change in a later task must update this line in that same task.
- Very long summary words must wrap, not overflow on 390 px.

## Gates

1. `board-check`: `python3 $POLIER/tools/check.py .` → exit 0 (before `pnpm install`).
2. `design-check`: `node tools/design-check/index.mjs .` → exit 0.
3. `changelog-entry`: `node tools/release/check-changes.mjs --task P0-22 --base main` → exit 0.

## Limits

- **Scope:** only `apps/web/preview/` and `.changes/`; gate records and screenshots under
  reviews/evidence are always allowed.
- **Stop:** 1 round; when blocked, `status: blocked` + reason.
