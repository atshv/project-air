# P3-03 — Auth service with self-hosted Ory Kratos

## Goal

`services/auth` validates sessions against self-hosted Ory Kratos, creates invited identities
through the Kratos admin API and exposes a signed test-session mode for integration tests; Kratos
runs from Compose with its identity schema, Mailpit courier and its own database.

**Why:** ADR-0007 — Kratos owns identities and credentials; the platform needs one session check
(AD-5) and invitations, nothing more.

**Satisfies:** D9

## Scope

- `infra/kratos/`:
  - `kratos.yml` — DSN from `KRATOS_DSN`, secrets and public/admin URLs from environment,
    self-service flows for password, code/magic-link login, registration, recovery and verification,
    courier SMTP pointing at the Compose Mailpit, session cookie settings (secure in production,
    SameSite=Lax), `log.level` from environment; no secrets committed (names in `.env.example`).
  - `identity.schema.json` — traits email (unique, verified) and display name; locale optional.
  - `infra/compose/compose.yaml` — extend the `kratos` service from P3-01: `kratos migrate sql`
    one-shot service before start, public `127.0.0.1:4433` and admin `127.0.0.1:4434` (fixed host
    ports outside the slot range), depends-on healthy Postgres, health check on the public API.
- `services/auth/`:
  - `src/kratos.ts` — small clients for the Kratos public API (login/registration/recovery/session)
    and admin API (create identity, recovery link, list identities) using `fetch`/`node:http`,
    with timeouts and typed errors; never log tokens or cookies.
  - `src/session.ts` — `GET /session`: forward the session cookie to Kratos
    `/sessions/whoami`, map the identity to `{accountId, email, displayName}`; no session → 401
    `AUTH_REQUIRED`.
  - `src/test-session.ts` — HMAC-signed test session header (`x-test-session`) accepted **only**
    when `AUTH_TEST_MODE=1` and `NODE_ENV !== "production"`; `POST /test/session` mints one for the
    integration tests; production startup refuses `AUTH_TEST_MODE=1`.
  - `POST /internal/invitations` (admin-token protected) — create an identity via the Kratos admin
    API and return its id; the workspace invitation itself is created by the platform in P3-04.
  - Unit tests with a stub Kratos HTTP server and the test-session mode; no live Kratos needed.
- `docs/versions.md` — Kratos image tag + digest pinned (v26.2.0, Apache-2.0) and any new package
  (none expected); `.env.example` names only.
- `.changes/P3-03-auth-kratos.md` (area `auth`, kind `minor`).

## Out of scope

- Platform routes and permissions (P3-04), RLS/SDK (P3-05), real e-mail delivery (Mailpit only),
  MFA/passkeys UI, Ory Hydra/OIDC provider, external IdPs.

## Acceptance

A1 WHEN the Compose stack is configured and started, THEN Kratos applies its migrations, starts
healthy and exposes the identity schema and flows; `docker compose config --quiet` exits 0.
A2 WHEN `GET /session` receives a valid Kratos session cookie, THEN it returns the account id,
e-mail and display name; without a session it returns 401 `AUTH_REQUIRED`; a stub-Kratos unit test
covers both.
A3 WHEN `AUTH_TEST_MODE=1` is set outside production, THEN `POST /test/session` mints a signed
test session that `GET /session` accepts; in production the service refuses to start with the test
mode enabled.
A4 WHEN `board-check`, `boundaries`, `unit` and `compose-config` run, THEN all exit 0 with records
committed.

## Specifications

- Node ESM/TypeScript as in P3-01; no new dependency, no framework; `fetch` is built in.
- Kratos is the only identity source; `services/auth` keeps **no** password or credential data.
- Session validation is server-side; cookies are forwarded only to Kratos, never logged, never
  stored in the platform database.
- Test-session HMAC: `base64url(accountId).base64url(expiry).signature` with a secret from
  environment; TTL short (≤ 1 h); the mode is impossible to enable with `NODE_ENV=production`.
- Error envelope matches the contract: `{code, messageKey, requestId}`; `AUTH_REQUIRED` maps to
  `errors.authRequired` (P1-05).
- The Kratos database is the shared `projectair_kratos` database for local development (documented
  limitation) and a per-environment database in production.

## Pitfalls

- Kratos needs its migrations run before start (`kratos migrate sql`); a start without them fails.
- Mailpit host port: inside the Compose network it is `mailpit:1025`, not `127.0.0.1:1025`.
- Do not expose the Kratos admin API beyond localhost; admin token from environment only.
- Unit tests must not depend on a running Docker/Kratos; use the stub server.
- `board-check` before any `pnpm` command; never log cookies or the DSN.

## Edge cases

- Expired/invalid Kratos session → 401 `AUTH_REQUIRED`, no stack trace.
- Kratos unreachable → 503 `INTERNAL` with a short message, readiness 503.
- Test-session with wrong signature/expiry → 401, never a 500.
- Duplicate invited e-mail → Kratos conflict mapped to `CONFLICT`/`errors.conflict`.
