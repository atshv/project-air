# P1-04 — Sync protocol messages

## Goal

The contract defines the WebSocket sync protocol as versioned JSON Schema with valid/invalid
fixtures: join/leave, operation batches, acknowledgements, presence, rejection and reconnect
catch-up.

**Why:** realtime (stage realtime) and the SDK need one message language over the contract
operations (AD-1, AD-2, AD-3).

**Satisfies:** D7

## Scope

- Layout: sync schema files live under `schemas/sync/` (the codegen reads only top-level
  `schemas/*.schema.json`, so a subdirectory keeps the generated model unchanged); sync fixtures
  live under `fixtures-sync/{valid,invalid}/`, outside the 77-fixture parity corpus
  (`fixtures/`), because the parity test locks that corpus size and tests must not change.
- Fixture-tree normalization (needed by the P1-06 `contracts` gate): move the entity fixtures to
  `fixtures/valid/<entity>/` and `fixtures/invalid/<entity>/`; operation fixtures stay flat in
  `fixtures/operation/`. Keep the 77-fixture parity corpus, the fixture wrapper format and all
  existing tests unchanged; update `index.mjs` and `test/support.mjs` accordingly.
- `packages/contracts/schemas/sync/` (or `sync.schema.json` with `$defs`): message envelope with
  `id`, `boardId`, `clientId`, `seq`/`serverSeq` where applicable, `type`, `payload`;
  - client → server: `hello` (auth token reference), `joinBoard`, `leaveBoard`,
    `operationBatch` (ordered operations from P1-02), `resyncRequest` (from serverSeq),
    `presence` (cursor, selection, name/colour reference);
  - server → client: `welcome` (serverSeq, board snapshot reference), `ack` (op ids, serverSeq),
    `operationBatch` broadcast, `presence`, `reject` (error code from P1-05 when available),
    `snapshot` (catch-up payload reference);
  - reconnect/catch-up: `resyncRequest` + `welcome`/`snapshot` rules; every acknowledged batch is
    durable (AD-2).
- Fixtures: valid and invalid example per message type plus reconnect sequence fixtures.
- Unit tests: schema parses, every message type has valid+invalid fixtures, ids/seq rules,
  operation batches reference the P1-02 operation schema, no unknown message types.
- `index.mjs` exports sync schema/fixture paths; README/ARCHITECTURE add a message table.
- `.changes/P1-04-sync-protocol.md` (area `contracts`, kind `minor`).
- Run codegen after the schema change (P1-03); generated files committed.

## Out of scope

## Specifications

- Keep contract version `0.1.0`; the tag happens in P1-06.
- JSON Schema 2020-12, `additionalProperties: false`, enums for message types, ISO timestamps,
  UUIDv7 ids; reference operation schemas with `$ref` instead of duplicating them.
- Sequence rules: monotonically increasing `serverSeq`; `ack` covers the batch; resync from a known
  seq; unknown/duplicate batches are invalid.
- Presence messages carry no operation data; operation batches carry only P1-02 operations.
- Tests use Node builtins only; no new dependencies.

## Pitfalls

- Do not implement a server; contract only.
- Do not change the operation schema semantics; extend as needed in the same task and update
  codegen/tests.
- Keep the C++ parity harness green: new schemas that are part of fixtures must regenerate cleanly.
- `check.py` scans `node_modules/`; run board-check before any install.

## Edge cases

- Empty operation batch → invalid.
- Batch with an unknown operation type → invalid.
- Resync with a future serverSeq → invalid with a clear reason.
- Presence for a board the client has not joined → invalid.
