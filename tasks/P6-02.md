# P6-02 — Auth UI and session: Kratos login, registration and recovery

## Goal

`services/auth` proxies the Kratos API login/registration/recovery flows (JSON endpoints, session
cookie, no token in the SPA) and `apps/web` gets the login/registration/recovery pages, logout,
session guard and the settings language switch; typed errors come from message files.

**Why:** the board list and every later page need an authenticated session; the own auth UI is the
ADR-0007 promise.

**Satisfies:** D12

## Scope

- `services/auth/` routes over the existing Kratos client and error mapping: `POST /v1/auth/login`
  (email + password; creates and submits the Kratos API login flow, forwards the session
  `Set-Cookie`), `POST /v1/auth/registration`, `POST /v1/auth/recovery` (start/recover where the
  provider supports it), `POST /v1/auth/logout` (logout flow + cookie clear); `GET /v1/session`
  stays as-is, and the existing `test/session` path stays behind its test flag. Controllers do not
  log credentials or session tokens; invalid input/credentials return typed contract errors.
- `packages/sdk/` auth/session client: `session.get()` (via the platform `/v1/session` or the auth
  service base URL configured in `ClientOptions`), `auth.login/registration/recovery/logout` with
  `credentials: "include"` and typed `ApiError`; `apps/web` reaches auth **only through the SDK**
  (ARCHITECTURE: no service imports/fetches in the app).
- `apps/web/` pages and state: login (email/password, inline validation, submit/disabled/error
  states, `autocomplete`/labels from messages), registration, recovery, a session guard
  (unauthenticated users are redirected to `/login` and back after login), logout in the account
  menu, and the settings page showing the signed-in account plus the working language switch. No
  token is written to `localStorage`/`sessionStorage`; the session stays in the HttpOnly cookie.
- `apps/web/` dev/e2e wiring: Vite dev proxy for `/v1` to the slot's platform/auth ports (read
  `.polier-slot`, no hardcoded ports) so cookies are same-origin in development; document the
  local start command (`services/auth`, `services/platform`) in the app README.
- Tests: auth route tests with the existing fake-Kratos pattern (success, invalid credentials,
  provider unavailable, cookie forwarding, logout, test-mode untouched); SDK auth resource tests
  with a fake fetch (methods, credentials, error mapping); web form validation helpers. `.changes/
  P6-02-<short-name>.md` (area `auth`, kind `minor`); message keys in `apps/web/messages/{en,de}.json`.

## Out of scope

- MFA/passkeys/social login UI, invitation UI and e-mail delivery (Kratos/Mailpit local), e2e
  (P6-08), board list (P6-03), SSR, a token-in-storage scheme.

## Acceptance

A1 WHEN valid credentials are submitted on `/login`, THEN the auth service proxies the Kratos flow,
sets the session cookie, the page redirects to `/boards`, and no credential or token is stored in
browser storage or logged; invalid credentials show a typed, localized error and the form stays.
A2 WHEN no valid session exists, THEN protected routes redirect to `/login`; after login the user
returns to the intended route; logout clears the cookie and redirects; the settings language switch
works and the session survives a reload.
A3 WHEN the task is done, THEN `board-check`, `boundaries`, `unit`, `typecheck`, `design-check` and
`language-check` exit 0 with records, the auth routes/SDK methods are documented, and the change
entry exists.

## Specifications

- Cookie handling: the auth service forwards the provider's session cookie (`HttpOnly`, `SameSite`
  as the provider sets it); the browser side never reads or stores it. Same-origin in dev via the
  Vite proxy; document the production cookie/domain rule.
- Errors: map Kratos flow errors to the project's typed error codes and message keys; never echo
  provider internals or credentials; 401 vs 400 vs 503 are distinguishable.
- The test-mode session header stays gated by the existing test flag; e2e may use it to run without
  a live Kratos (documented), while the real flow is exercised by the route tests.
- Validation: server-side validation is authoritative; the UI mirrors it for quick feedback.
- Imports: `services/auth` and `packages/sdk` per `may_import` (`boundaries` gate); `apps/web` only
  the allowed packages; no direct `fetch` to auth endpoints outside the SDK.
- Languages: every visible string and aria label in `en.json`/`de.json`; German default.

## Pitfalls

- Kratos API flows need a CSRF token for submission — create and submit in one service call, never
  expose the flow object to the browser.
- `credentials: "include"` with a Vite proxy: cookies must be same-origin; a missing proxy makes
  login appear to succeed but the session guard loop.
- A redirect loop happens if the session guard runs before the session probe resolves; render a
  neutral loading state.
- Do not store the session token to work around cross-origin cookies; fix the proxy/domain.
- Logout must clear the cookie even when the provider call fails; surface the result honestly.
- Tests must not require a live Kratos; the fake covers the route mapping.
