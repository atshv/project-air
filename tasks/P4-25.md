# P4-25 — Contract 0.2.0: zone parent reference and reorder (z) operation (L08/L13)

## Goal

The contract gains (a) an optional zone parent reference on board items and (b) a `reorder` operation
that stores a new fractional `z` for one item with its inverse (the previous `z`); the contract
version moves to `0.2.0` everywhere, fixtures, TS/C++ codegen and parity are updated, the `moveZone`
`zoneId` description is corrected, and an ADR records the Q17 zones-as-containers decision.

**Why:** Q17 approved zones as containers, and L13 stores "last moved on top" as a fractional `z`
that must be one contract operation with its inverse (AD-1); P4-05 found no `reorder`/`z` operation in
0.1.0, so both changes share the 0.2.0 bump (database work is P4-26).

**Satisfies:** D10

## Scope

- **Version 0.2.0 (ADR-0005):** bump `board.contracts[]`, every schema `$id` and the root
  `contractVersion` in one commit; document it in `docs/contracts.md` (limits unchanged).
- **Zone parent reference:** an optional nullable parent (zone id) on the board items that can live
  in a zone (cards and blocks; `null`/absent means board level). Zones never carry a parent (no nested
  zones in v1); a schema rule or fixture must reject nesting. Update valid and invalid fixtures,
  including a dangling parent and a nested zone.
- **Reorder operation:** add an operation type `reorder` with payload `{itemId, z}` and its inverse
  `{itemId, z}` (previous value), `z` as the contract's fractional-index string; add valid and invalid
  fixtures, include it in the operation corpus and the TS/C++ generated types, and keep every
  dependant type in the same task (AD-3).
- **`moveZone` description fix:** the schema describes `payload.zoneId` as the parent zone while the
  valid fixture and inverse use it as the moved zone id; correct the description (and any generated
  docs) without changing the wire shape.
- **Codegen and parity:** regenerate `generated/types.ts` and the C++ header, keep the TS/C++
  fixture-parity suites green, and update `docs/contracts.md` (operation list, parent reference,
  version).
- **ADR:** ADR-0010 (written with the stage plan) records zones-as-containers, the nullable parent,
  no nested zones in v1 and the follow-ups P4-26/P4-27; refine it only if the implementation forces a
  change.
- **Board:** only the `contracts[]` entry version/schema list in `board.json`; the Lead owns all other
  board fields.
- `.changes/P4-25-<short-name>.md` (area `contracts`, kind `minor`).

## Specifications

- Versioning is one atomic change: no schema may stay at `0.1.0` when the root constant moves; codegen
  and parity run in the same task (ADR-0005).
- Every new rule needs a valid and an invalid fixture; the fixtures are the TS/C++ parity corpus.
- The reorder payload stores the fractional-index string, not a numeric z; the inverse carries the
  previous string, and no new operation duplicates `moveCard`/`resizeCard`.
- The parent reference is additive and nullable; old fixtures without a parent stay valid.
- Do not change limits, visibility or error codes (ADR-0004).
- `board.json` changes are limited to the `contracts[]` metadata.

## Pitfalls

- Forget one `$id` or the C++ header and parity fails; regenerate through the package script.
- A nested-zone fixture validated only by TS (or only by C++) breaks parity.
- Existing consumers compile against the generated types; keep fields additive and run `pnpm typecheck`.
- `check.py` scans `node_modules/`; run `board-check` before `pnpm install`.

## Edge cases

- A parent reference to a missing zone id: decide whether the schema or the fixtures reject it.
- Reorder and deletion of the same item: the inverse must not resurrect a deleted item.
