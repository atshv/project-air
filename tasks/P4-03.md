# P4-03 — Engine-core perf gate and L01 basis

## Goal

The perf harness gains an engine-core scenario — 10,000 mixed board objects with continuous pan and
zoom, p95 <= 16.7 ms and no frame interval above 16.7 ms after warm-up — plus the L01 basis run with
500 cards and 50 zones; the gate writes JSON evidence and `docs/gates/perf.md` and `docs/quality.md`
define the `perf` gate.

**Why:** L01 and the stage exit need a measured basis and a repeatable gate. Q18 fixes the
engine-core target at 10,000 objects, and later drawing and interaction tasks must be comparable
against this basis.

**Satisfies:** D10

## Scope

- `packages/engine/test/perf/run-perf.mjs`: keep the default `perf-baseline` mode (50,000
  rectangles) untouched, and add `--scenario engine-core` with two modes:
  - **interactive run** on the 10,000-object board scene: the page must report the exact object,
    zone and block counts from `packages/test-kit`, the warm-up and sample counts; the harness drives
    continuous pan and zoom (a deterministic camera path through the document, one `setCamera` per
    frame) and records frame intervals, p50/p95/p99, mean, max, the interval histogram and the count
    of intervals above 16.7 ms;
  - **L01 basis/final run** on the 500 cards + 50 zones sample board: pan and zoom during sampling,
    record the same metrics plus maximum frame duration; `--record basis` writes the basis before
    the drawing tasks, `--record final` writes the final proof and additionally asserts that the
    command-buffer instance count matches the culled visible set, not the document size.
- Assertions before a pass: exact scene counts, warm-up and sample counts, a positively identified
  real GPU (fail-closed), unlocked display clock, no `infra`/`busy` result. A failed assertion is
  `infra` (exit 3) or a failure, never a pass.
- Evidence: `reviews/evidence/<task>-perf-basis-<timestamp>.json`, `...-perf-final-<timestamp>.json`
  and the gate record, each with hardware, OS, browser, flags, renderer, sizes and numbers.
- `docs/gates/perf.md`: verify and refine the plan-committed `perf` section and mirror its constants
  in the harness.
- `docs/engine/perf-baseline.md`: add an engine-core section with the basis numbers, date, evidence
  paths and the M2-proxy caveat; never rewrite the spike numbers. `docs/quality.md` only on a
  correction.
- `.changes/P4-03-<short-name>.md` (area `engine`, kind `minor`).

## Out of scope

- Drawing, gestures, text or backend changes in the engine; new scenes beyond the two named.
- Loosening a budget or dropping a measurement; changing the spike's `perf-baseline` numbers.
- WebGPU measurement as a gate (an observation record is allowed but never a gate pass).

## Acceptance

A1 WHEN `node packages/engine/test/perf/run-perf.mjs --scenario engine-core` runs, THEN it measures
the 10,000-object interactive scenario and exits 0 only with p95 <= 16.7 ms, zero frame intervals
above 16.7 ms and a positively identified real GPU; the JSON records every metric and assertion.
A2 WHEN the L01 basis/final mode runs on 500 cards + 50 zones, THEN it records pan/zoom metrics; the
final mode proves the scene under 50 ms with instance count equal to the culled visible set.
A3 WHEN the basis record exists, THEN every later measurement is compared with it and must stay
within basis + 10 %, written into the task result and the gate record.
A4 WHEN the task is done, THEN `board-check` and `perf` exit 0, `docs/gates/perf.md`
matches the harness and `docs/engine/perf-baseline.md` quotes numbers with date and path.

## Specifications

- Scenario values are constants mirrored by `docs/gates/perf.md`; a change touches both. The 10,000
  objects are a board mix (cards, zones, blocks), not a rectangle grid.
- The camera path is deterministic (one zoom cycle plus a fixed pan sweep) and must not replace the
  document or rebuild the spatial index; if it does, fix the harness before measuring.
- Frame intervals are measured after warm-up only; the display clock stays unlocked and the
  display-locked control stays an observation, never a pass.
- The harness manages only its own server and browser, removes its temporary folder and reads the
  port from `.polier-slot`. If the sandbox refuses Chrome, record the error and ask for a one-shot
  wider approval.

## Pitfalls

- The "no interval above 16.7 ms" assertion can flag GC or scheduling noise on an 8 GB machine;
  re-run once on an idle machine and record it, but never silently loosen the budget.
- A stale playground or WASM build measures the wrong code; rebuild bridge and WASM first and
  record the build size.
- The L01 basis must be measured before the drawing tasks change the pipeline; if it is measured late,
  say so in the record.
- `check.py` scans `node_modules/`; run `board-check` before any `pnpm` command.

## Edge cases

- A machine without a real GPU: `infra`, exit 3, repeated later — not a pass.
- The spike's static baseline and the new pan/zoom basis are not comparable; keep the records apart
  and explain it.

## Gates

1. `board-check`: `python3 $POLIER/tools/check.py .` -> exit 0.
2. `perf`: `python3 $POLIER/tools/gate.py --task P4-03 --name perf --shell "node packages/engine/test/perf/run-perf.mjs --scenario engine-core"` -> exit 0, exclusive lock, JSON evidence written.
