# P1-02 — Operations, inverse operations and group

## Goal

The contract defines every board change as one operation with an inverse, plus a `group` operation
that bundles several operations into one gesture, with fixtures and unit tests (AD-1).

**Why:** undo/redo, realtime sync and the engine all depend on one operation vocabulary; one gesture
= one operation.

**Satisfies:** D7

## Scope

- `packages/contracts/`: `schemas/operation.schema.json` and one schema (or discriminator) per
  operation type; extend `board-content` fixtures as needed:
  - `createNote` / `updateNote` / `deleteNote` (note exists once, AD-4; delete affects placements),
  - `createCard` / `moveCard` / `resizeCard` / `deleteCard`,
  - `createZone` / `moveZone` / `resizeZone` / `deleteZone` (with content policy),
  - `createBlock` / `moveBlock` / `resizeBlock` / `updateBlock` / `deleteBlock`,
  - `createEdge` / `deleteEdge`,
  - `group` (ordered child operations, one inverse = reversed inverses),
  - every operation carries `id`, `boardId`, `actorId`, `createdAt`, `type`, `payload` and its
    inverse (either an embedded inverse operation or a documented pair).
- Fixtures: one valid and one invalid example per operation type plus a valid and an invalid
  `group`; fixtures continued in the existing `{schema, valid, reason, data}` wrapper.
- Unit tests: operation schema parses, every type has a fixture pair, every operation has exactly
  one inverse, `group` child operations validate and the group inverse reverses order, minimum
  values/size limits from P1-01 are respected.
- `index.mjs` exports the operation schema id/path; `packages/contracts/README.md` and
  `ARCHITECTURE.md` get an operation table and the inverse rule.
- `.changes/P1-02-operations.md` (area `contracts`, kind `minor`, one English line).

## Out of scope

  engine/server implementation, undo stack behaviour (engine stage).
- New dependencies; the contract version stays `0.1.0` until the stage tag (P1-06).

## Specifications

- **One operation = one gesture** (`AD-1`); the server is the source of truth (`AD-2`); the engine
  never writes directly.
- **Inverse:** define the inverse payload for every type; for updates store the previous values
  needed to restore; for deletes store the object; for creates the inverse is the matching delete.
- **Group:** `group.children` is an ordered list of operations; its inverse is the reversed list of
  child inverses; groups do not nest (document).
- **Validation:** reuse the `$defs`/`$ref` style of P1-01, `additionalProperties: false`, enums for
  `type`, ISO timestamps, UUIDv7 ids.
- **Tests:** Node builtins only; assert one inverse per type, group reversal, fixture coverage and
  the size limits from P1-01.
- **Version:** keep `$id` and `contractVersion` at `0.1.0`; do not invent a second version.

## Pitfalls

- Do not implement undo behaviour or a server; only the contract.
- Do not change the P1-01 entity schemas in a way that breaks existing fixtures without updating
  them and the tests in the same task.
- A delete operation must describe what happens to placement vs. note content (AD-4).
- `check.py` scans `node_modules/`; run `board-check` before any install.
- `.changes` entry is required for this code change.

## Edge cases

- Update operations on absent fields → invalid; partial updates must be explicit.
- Group with an empty child list → invalid.
- Group containing a group → invalid (no nesting in v1).
- An inverse with mismatching board/target ids → invalid.
