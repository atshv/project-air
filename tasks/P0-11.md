# P0-11 — Canvas acceptance catalogue

## Goal

`docs/canvas-acceptance.md` exists: every canvas work order becomes one catalogue entry with
goal, target values, states, do-nots, acceptance, package, stage, evidence and status, so the
engine and web phase gates can be checked against it.

**Why:** stage gates for engine-core and web-app say "all canvas work orders done"; without the
catalogue that sentence cannot be checked, and a UI task without numbers is not ready.

**Satisfies:** D3

## Scope

- Create `docs/canvas-acceptance.md` (English).
- One entry per row of blueprint section 21.2: `L00`–`L20` (21 entries). Every entry has all
  fields: **Goal · Target values · States · Do not · Acceptance · Package · Stage · Evidence ·
  Status**.
- Fill the entries from the blueprint table **and** the detailed work orders in
  `reference/docs/canvas-polish.md`: the blueprint table is the compressed summary; the reference
  carries the detailed target values and acceptance checks. Keep both, do not drop numbers.
- Add a mapping table: entry ID ↔ reference work-order ID (`C1`, `C2`, … `C19`, including
  `C13a`/`C13b`). A reference work order that has no entry is listed under "Unassigned reference
  work orders", not turned into a new entry.
- Add the reference's "Querschnitt" rules as a short section that applies to every entry, and a
  "How to use" section: how a task cites an entry, and the status values `open` (initial),
  `fulfilled`, `deviated + owner approval`.
- Add an "Open points" section for numbers or rules that differ between blueprint 21.2 and the
  reference, and for entries blocked by board open questions `Q15` (collisions, L13) and `Q16`
  (trackpad, L15); their status stays `open`.
- All entries start with status `open`; nothing is `fulfilled` in this task.

## Out of scope

- The check tool (`P0-13`), the design tokens (`P0-12`) and any engine or web code.
- New work orders, new target values or new gates.
- Anything under `reference/` (read-only) or in `docs/design-rules.md` (owned by P0-10).

## Acceptance

A1 WHEN `docs/canvas-acceptance.md` is read, THEN it contains entries `L00`–`L20` and every
entry has all nine fields named in the goal, with status `open`.
A2 WHEN an entry is compared with blueprint 21.2 and its mapped reference work order, THEN every
target value is present; the mapping table covers every reference work order (`C…`) and lists the
unassigned ones; no value is invented.
A3 WHEN `python3 $POLIER/tools/check.py .` runs after the task, THEN it exits 0 (no broken links)
and the file names no earlier-prototype product, vendor or file name.

**Budget:** ≤ 25k tokens input.

## Specifications

- **New file:** `docs/canvas-acceptance.md`.
- **Language:** English; German UI example strings keep `ss`, never `ß`.
- **Stage mapping:** blueprint task IDs (`P2-03`, `P4-02`, `P6-02`, `P8-05`, …) do not exist on
  this board yet. Name the board stage id instead (phase 2 → `engine-spike`, phase 4 →
  `engine-core`, phase 5 → `realtime`, phase 6 → `web-app`, phase 8 → `hardening`) and keep the
  blueprint ID in brackets as a note.
- **Packages:** use the paths from `board.json` → `packages[]` (`packages/engine`, `apps/web`,
  `packages/editor`, `packages/contracts`, `packages/ui-kit`, `packages/sdk`, `packages/crdt`,
  `services/platform`, `services/sync`).
- **Evidence:** name only gates that exist in `docs/quality.md` (`cpp-unit`, `e2e`, `perf`,
  `visual`, `design-check`, `language-check`, `api-tests`) and artefacts under
  `reviews/evidence/`; do not invent gate names.
- **Links:** create markdown links only to files that exist now (`ARCHITECTURE.md`,
  `docs/design-rules.md`, `docs/module-map.md`, `docs/quality.md`, `board.json`); mention future
  paths such as `tools/design-check/` as code spans.

## Pitfalls

- The 21.2 table is compressed: for `C`-mapped entries the reference has the detailed values.
  Merge both sources instead of copying only the short table.
- Do not turn "Messwerte", "Erweiterungen" or "Prozess" from the reference into catalogue entries;
  they belong in "Open points", "Deferred" or "How to use".
- Do not link to files that do not exist yet; `check.py` fails on broken markdown links.
- The design law is binding: use its terms (tokens, layers, states) instead of inventing new ones.
- Status is `open` everywhere; do not mark anything fulfilled to look complete.

## Edge cases

- One blueprint entry covers two reference work orders (`L01` = `C13a` + `C13b`) → one entry with
  both IDs in the mapping table.
- A reference work order without a blueprint entry → list it under "Unassigned reference work
  orders" with one line why, and do not invent an `L` entry.
- A target value only in the reference but missing from blueprint 21.2 → keep the reference value
  and mark the source (`reference`), or list the difference in "Open points"; do not delete it.
- A rule tied to the earlier prototype (named product, file path, vendor) → drop it and list it in
  "Open points"; never copy prototype names into the catalogue.
