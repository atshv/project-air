# P3-02 — PostgreSQL schema, migrations and RLS policies

## Goal

Versioned migrations create the workspace/board/note/card schema with constraints and indexes, and
row-level security enforces workspace membership for the restricted `app_user` role; migration and
policy tests run against the slot database.

**Why:** the API and the isolation tests need one schema and one policy set; AD-4 (a note exists
once) and AD-5 (authorisation checked twice) bind here.

**Satisfies:** D9

## Scope

- `infra/migrations/` — numbered SQL migrations (never edit an applied file):
  - `profiles` — `account_id uuid primary key` (the Kratos identity id), `display_name`,
    `locale`, timestamps; one row per account.
  - `workspaces` — `id uuid primary key`, `name`, `owner_account_id`, timestamps.
  - `workspace_members` — `(workspace_id, account_id)` primary key, `role` enum
    (`owner`/`editor`/`reader`), timestamps; owner row created with the workspace.
  - `boards` — references `workspace_id` + owner; title, visibility (`private`/`workspace`/`link`
    per ADR-0004), archived, timestamps.
  - `notes` — references `workspace_id`; title, timestamps; a note exists once (AD-4).
  - `cards` — references `board_id` and `note_id`, `zone_id` nullable, geometry
    (`x`, `y`, `width`, `height` double precision, minimum 176×80), fractional `z` text,
    timestamps.
  - Foreign keys with `on delete` rules that keep orphans impossible; unique/index constraints for
    the list queries (workspace→boards→cards, note lookups).
- Row-level security on every table: `enable` **and** `force`; policies for `app_user` per table:
  - `profiles`: a row is visible/updatable only when `account_id = current account`.
  - `workspaces`/`boards`/`notes`/`cards`: read for every member of the workspace
    (`owner`, `editor`, `reader`); write for `owner`/`editor` per the permission matrix; workspace
    delete and membership changes only for the owner. RLS must also block inserting rows into a
    foreign workspace.
  - A small `app.current_account_id()` helper reads `current_setting('app.account_id', true)` and
    returns `uuid` (null when unset), so a missing setting yields no rows instead of an error.
- Grants for `app_user`: `select/insert/update/delete` on the tables (no `BYPASSRLS`, no
  `SUPERUSER`, no ownership); migration owner stays the Compose superuser.
- Tests (`services/platform/test/migrations/*.mjs`) against the slot database: migrations apply
  and rerun idempotently; a fresh reset leaves the expected tables/constraints; invalid rows
  (orphan board, card without note, too-small card) are rejected; RLS is enabled and forced on
  every table and `app_user` has no bypass; a first policy smoke as `app_user` (own workspace
  visible, foreign workspace invisible).
- `tools/dev/setup`/`reset-db` kept working; update `docs/gates/postgres.md` if a command or role
  name changes.
- `.changes/P3-02-postgres-rls.md` (area `platform`, kind `minor`).

## Out of scope

- API endpoints (P3-04), auth/Kratos (P3-03), the full RLS isolation suite and SDK (P3-05),
  performance indexes beyond the list queries, audit/events tables.

## Acceptance

A1 WHEN the migrations are applied to a fresh slot database, THEN the six tables exist with the
constraints/indexes named above and `schema_migrations` records every version.
A2 WHEN RLS is inspected, THEN every table has RLS enabled and forced, `app_user` is not
superuser/owner and has no `BYPASSRLS`, and the policies implement the permission matrix.
A3 WHEN the migration tests run, THEN applying twice is idempotent, invalid rows are rejected and
the `app_user` policy smoke shows own-workspace rows only.
A4 WHEN `board-check`, `unit` and a database reset run, THEN all exit 0 with records committed.

## Specifications

- UUIDs are UUIDv7, generated by the application; the database stores plain `uuid` (no extension).
- Timestamps are `timestamptz not null default now()`; geometry uses `double precision`; `z` is
  the contract's fractional-index string (1–64 alphanumerics).
- Migration names `NNNN_<name>.sql`, ascending, immutable once merged; the runner records a
  SHA-256 checksum and fails when an applied file changed.
- Tests connect as `app_user` for the policy smoke and as the migration owner for setup; never
  hard-code a connection string, read it from the environment/.polier-slot.
- RLS tests are destructive/order-sensitive: tasks declare `"exclusive": ["db"]` and run only
  against the slot database; close pools in `after()`.

## Pitfalls

- RLS is invisible to a superuser: a green test with `POSTGRES_USER` proves nothing. The smoke must
  use `app_user`.
- `SET LOCAL app.account_id` only lives inside a transaction; reset/close the connection so the next
  request does not inherit a foreign account.
- Cursors/counts must respect RLS as well; a `left join` from a foreign table can leak existence.
- Never edit an applied migration; add a new numbered one. Never touch slot 0.
- `board-check` before any `pnpm` command if `node_modules/` exists.

## Edge cases

- Missing `app.account_id` → zero rows, never an error and never all rows.
- Owner row and workspace created atomically; a workspace without an owner membership is an error.
- Deleting a board cascades its cards; deleting a note with cards is refused (or the cards are
  deleted explicitly in the API task).
- Duplicate membership for the same account/workspace fails with a unique violation.
