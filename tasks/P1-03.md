# P1-03 — Codegen TS + C++ with identical fixtures

## Goal

A deterministic code generator turns the contract schemas into TypeScript types and a C++ header;
the same fixtures produce identical results in TypeScript and C++ (the contract's proof for AD-3).

**Why:** engine (C++) and backend/web (TS) must read one contract identically before any product
code depends on it.

**Satisfies:** D7

## Scope

- `packages/contracts/`:
  - `codegen.mjs` (Node builtins only): reads `schemas/` and writes committed generated files:
    `generated/types.ts` (entity and operation types, enums, discriminated unions, inverse pairs)
    and `generated/contract.h` (C++ structs/enums for the same model, `#pragma once`, namespaced,
    deterministic ordering).
  - A deterministic output (stable ordering, LF, no timestamps); a second run must produce no diff.
  - Fixture parity harness:
    - TS side: read every fixture in `fixtures/` and produce a canonical result per fixture
      (schema, validity, and a normalized description: entity/operation type, ids, inverse type,
      sorted required keys);
    - C++ side: a test-only C++ program (compiled with `clang++`/`g++` directly, no CMake needed)
      that reads the same fixtures with a small self-written JSON reader under
      `packages/contracts/test/cpp/` (test-only, no third-party dependency), builds the same
      canonical result and prints it deterministically;
    - the unit suite compares both result sets and fails on any difference.
  - `package.json` scripts: `codegen` (`node codegen.mjs`) and `test` (TS tests + parity harness);
    no dependencies.
  - README/ARCHITECTURE: generated files, codegen command, parity harness, clang requirement.
  - `.changes/P1-03-codegen.md` (area `contracts`, kind `minor`).
- Contract version stays `0.1.0`; generated output lives under `packages/contracts/generated/` and
  is committed.

## Out of scope

- Sync messages (P1-04), API errors (P1-05), prose/ADR/tag (P1-06), runtime validation in the
  engine or server, CMake/Emscripten setup (engine stage).
- New dependencies; the C++ compiler is the local `clang++` (or `g++` fallback) already installed.

## Acceptance

A1 WHEN `pnpm --filter ./packages/contracts run codegen` runs twice, THEN the generated TS and C++
files are byte-identical to the committed ones (`git diff --exit-code` clean) and contain the
entity/operation model with version `0.1.0`.
A2 WHEN the generated TypeScript types are compiled/checked, THEN entity and operation types,
enums, discriminated operation payloads and inverse pairs are present and typecheck (package
`typecheck` green).
A3 WHEN the parity harness runs, THEN the TS and C++ canonical results match for **every** fixture
(valid and invalid), and the C++ program compiles with `clang++`/`g++` without third-party
libraries; a deliberately mismatching fixture/marker fails the parity check.
A4 WHEN `board-check`, `codegen` and `unit` gates run through `gate.py`, THEN all exit 0 with
records committed; `check.py` exits 0 (before `pnpm install`).

## Specifications

- **Generator:** Node ESM, builtins only; input = schema files, output = `generated/types.ts` and
  `generated/contract.h`; stable ordering (schemas sorted, properties sorted, enums sorted);
  include the contract version and a generated-file banner ("do not edit").
- **TS types:** one interface/type per entity, block-type union, operation union with payloads and
  the single embedded inverse pair; no runtime validator required in this task beyond the parity
  harness.
- **C++ header:** matching structs/enums for the entities and operation envelope; use
  `std::string`, `std::vector`, `std::optional`; no engine code, no template magic.
- **Parity harness:** canonical output must be deterministic and comparable (sorted keys, sorted
  arrays where order is not semantic); the C++ reader lives under `test/cpp/` and is test-only.
  The harness may shell out to the compiler; it must skip with a clear message only if no C++
  compiler is available (never silently pass).
- **Gate commands:** report the exact `codegen` and `unit` commands for `docs/quality.md`.
- **No generated file may be edited by hand**; the gate catches drift.

## Pitfalls

- Do not add a JSON/Schema library; write only the small test-side JSON reader.
- Do not emit absolute paths or timestamps in generated files.
- Keep the generated C++ header compilable with `-std=c++20 -Wall -Wextra`.
- Do not change the schemas/fixtures to make parity easy; fix the harness instead.
- `check.py` scans `node_modules/`; run board-check before any install.
- `.changes` entry is required.

## Edge cases

- Invalid fixtures must be described identically (schema, validity=false, reason) by both sides;
  the canonical form may omit schema-invalid payloads but must keep the same validity verdict.
- A fixture referencing a schema with `$ref`s → both sides resolve the same effective type name.
- No compiler available → `unit` fails with a clear message, not a skip that hides the gap.
- Missing/extra generated files → codegen gate fails.

## Gates

1. `board-check`: `python3 $POLIER/tools/check.py .` → exit 0 (before `pnpm install`).
2. `codegen`: `pnpm --filter ./packages/contracts run codegen && git diff --exit-code -- packages/contracts` → exit 0.
3. `unit`: `pnpm --filter ./packages/contracts test` → exit 0 (includes the C++ parity harness).
