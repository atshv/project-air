# P3-06 — Contract-valid account IDs (Kratos identity mapping)

## Goal

The platform maps external Kratos identity ids to contract-valid UUIDv7 account ids, so a real
session produces v7 `ownerId`/account values; a migration adds the mapping, session resolution
creates or reuses it, and api-tests cover the v4-identity path.

**Why:** the P3-04 review found that Kratos identity ids are UUIDv4 while the contract's account
and `ownerId` values are UUIDv7 — real users could not create contract-valid workspaces without
this mapping (F2).

**Satisfies:** D9

## Scope

- `infra/migrations/0004_account_mapping.sql`:
  - `app.profiles` gains `kratos_identity_id uuid` with a unique partial index (one profile per
    Kratos identity) and a comment that `account_id` is the platform's contract-valid UUIDv7 id;
    existing rows (none in the stage DB, but be safe) are backfilled only if `account_id` is the
    identity id; no destructive changes.
  - RLS remains unchanged: `account_id` is the RLS key; the mapping is looked up by the platform
    under `app_user` (profiles_select_self cannot see other accounts — the lookup helper must be a
    SECURITY DEFINER function or a policy-safe query, granted to `app_user`, returning only the
    mapped id for the session identity; do not leak other rows).
- `services/platform/src/auth/session.ts` + `src/db/account.ts`:
  - session resolution accepts the auth service's `accountId` (Kratos identity id in production):
    if it is a UUIDv7, use it as the account id (test sessions and future Kratos versions);
    otherwise resolve the profile by `kratos_identity_id`; if none exists, generate a UUIDv7
    account id and insert the profile with the mapping in one transaction (`ON CONFLICT` safe for
    concurrent first requests), then continue with the mapped id. Repeated requests return the same
    account id.
  - Never expose the Kratos identity id in API responses (contract entities stay v7 only).
- `services/platform/test/api/*`: a regression case with a v4 identity id: first request creates a
  profile mapped to a generated v7 id, workspace/board creation returns v7 `ownerId`, a second
  request with the same v4 identity gets the same account and its resources; no duplicate profile.
- `docs/adr/ADR-0008-api-session-model.md`: extend the session/account section with the mapping
  rule (v7 identity = account id; v4 identity = mapped v7 account id; mapping unique per identity).
- `.changes/P3-06-account-mapping.md` (area `platform`, kind `minor`).

## Out of scope

- Changing the contract schemas or its version; auth service changes (it keeps returning the
  identity id as `accountId`); member/invitation routes; migrating historical data (none yet);
  UI.

## Acceptance

A1 WHEN a session carries a UUIDv4 identity id, THEN the platform creates or reuses one profile
with a generated UUIDv7 `account_id` and the identity id stored once (`kratos_identity_id` unique),
and API responses contain only UUIDv7 account/owner ids.
A2 WHEN the same v4 identity calls again, THEN it resolves to the same account id; two concurrent
first requests do not create two profiles; a v7 session id is used as the account id directly.
A3 WHEN `api-tests` run, THEN they include a v4-identity regression (create workspace/board/note,
same account on the next request, no duplicate profile) and the suite stays green.
A4 WHEN `board-check`, `unit` and `api-tests` run, THEN all exit 0 with records committed; the
migration applies on the existing slot database and on a fresh reset.

## Specifications

- Account ids stay UUIDv7; the Kratos identity id is an external key, never a contract id.
- Mapping helpers run as `app_user`; a SECURITY DEFINER function needs `REVOKE ALL FROM PUBLIC` and
  an `app_user` grant, and must return only the mapped account id for the given identity id.
- The profile insert uses the existing `profiles_insert_self` policy by setting
  `app.account_id` to the newly generated v7 id for that one transaction; the mapping row is part
  of the same insert, no second profile.
- Migration is additive and reversible in spirit (no data loss); never edit 0001–0003.
- Tests keep the slot DB migrated+empty afterwards; the task is `exclusive: ["db"]`.

## Pitfalls

- Do not put the v4 identity id into any contract field; that is the defect this task fixes.
- `ON CONFLICT` on `kratos_identity_id` + unique index is the concurrency guard; a plain
  select-then-insert races.
- A SECURITY DEFINER function that returns identities would leak other accounts; return only the
  account id and keep the search path safe.
- `board-check` before any `pnpm` command; never edit an applied migration.

## Edge cases

- Unknown v4 identity, existing v4 identity, v7 identity, invalid identity id (auth already
  validated), two concurrent first requests, profile insert conflict.
- Account id generated but profile insert fails → the transaction rolls back, no orphan identity
  row; retry creates it once.
