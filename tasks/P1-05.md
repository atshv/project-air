# P1-05 — API resources and error codes

## Goal

The contract defines REST resource envelopes for workspaces, boards, notes and cards plus one
error envelope whose codes map to translation keys `errors.<CODE>` in the message files.

**Why:** the SDK, backend and web app need one resource/error shape; user-visible errors must be
translatable (AD-8) without code changes.

**Satisfies:** D7

## Scope

- `packages/contracts/schemas/api/`: request/response envelopes for workspace, board, note and card
  (list, get, create, update, delete), pagination and `requestId`; `errors.schema.json` with codes
  (`AUTH_REQUIRED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION`, `CONFLICT`, `RATE_LIMITED`, `INTERNAL`)
  and a required `messageKey` equal to `errors.<CODE>`.
- `apps/web/messages/de.json`, `en.json`, `en-XA.json`: add one message per error code under
  `errors` (ICU-safe; German `ss`, never `ß`); regeneration of the pseudo locale via the existing
  `--write-pseudo`.
- Fixtures valid+invalid per resource/error shape; tests assert every error code has a message key
  in every locale and the resource envelopes reference the P1-01 entities.
- `index.mjs` exports api/error paths; README/ARCHITECTURE update.
- `.changes/P1-05-api-errors.md` (area `contracts`, kind `minor`); codegen and language-check run
  after the changes; generated files committed.

## Out of scope

- Server routes/auth implementation, UI, retries, logging, error transport over HTTP/WebSocket
  (server stages), prose/ADR/tag (P1-06).

## Acceptance

A1 WHEN the API schemas are read, THEN resource envelopes and the error envelope exist with
versioned schemas and the fixed error-code enum.
A2 WHEN message files are read, THEN every error code has exactly one `errors.<CODE>` key in de,
en and en-XA, and language-check exits 0.
A3 WHEN `pnpm --filter ./packages/contracts test` and the `codegen` gate run, THEN tests pass,
generated files are unchanged after regeneration, and records are committed.
A4 WHEN `python3 $POLIER/tools/check.py .` runs, THEN it exits 0 (before `pnpm install`).

## Specifications

- Contract version stays `0.1.0`; tag in P1-06.
- JSON Schema 2020-12, `additionalProperties: false`, UUIDv7 ids, ISO timestamps; resources use
  `$ref` to the P1-01 entities; list responses carry `items` + `nextCursor`; error envelope carries
  `code`, `messageKey`, `details?`, `requestId`.
- Error messages are short, du-form, no exclamation marks, `ss`; one phrase per code.
- The `messageKey` value is exactly `errors.<CODE>`; tests fail on missing/extra keys or a
  mismatch.
- Tests Node builtins only; language-check and codegen gates must stay green.

## Pitfalls

- Do not hard-code German text in schemas; only the key.
- Do not add a second error-key scheme.
- Keep `errors` message objects flat enough for the existing language-check (key parity across
  locales).
- `check.py` scans `node_modules/`; run board-check before any install.

## Edge cases

- Unknown error code in a fixture → invalid.
- A code without a translation key in one locale → language-check fails.
- Empty list → `items: []`, `nextCursor: null`.
- Validation errors list field paths, not user text.
