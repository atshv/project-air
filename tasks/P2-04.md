# P2-04 — Performance baseline and measured report

## Goal

A reproducible browser benchmark measures 50,000 rectangles at 60 fps on the recorded hardware,
writes a measured report and a `perf-baseline` gate record, and documents the WASM size.

**Why:** the engine-spike exit criterion needs a measured number and a report; engine-core and the
quality stages compare against this baseline.

**Satisfies:** D8

## Scope

- Harness `packages/engine/test/perf/run-perf.mjs` (Node builtins only):
  - reads the slot web port from `.polier-slot`, copies the built playground + WASM artifacts into a
    temporary served folder, starts and stops **its own** static server, then launches Chrome with
    WebGL enabled;
  - navigates the playground with a benchmark query (`?bench=50000&samples=600&warmup=120`),
    receives the frame-time samples from the page (console/JSON channel), computes p50/p95/p99 and
    mean fps, writes `reviews/evidence/P2-04-perf-<timestamp>.json` with hardware, OS, browser
    version, build flags, sample count and results;
  - exits 0 only when p95 frame time ≤ 16.7 ms (≈ 60 fps) at 50,000 rectangles; otherwise prints the
    numbers and exits 1. A record with `infra`/`busy`/`timeout` is not evidence.
- Playground benchmark mode: deterministic 50,000-rectangle document, camera at a representative
  pan/zoom level, rAF-driven sampling after warm-up, no fps-counter throttling; the normal demo
  without the query keeps its behaviour.
- Measured report `docs/engine/perf-baseline.md`: method, hardware, browser, build flags, sample
  count, p50/p95/p99, mean fps, WASM gzip size, screenshots/links, and the reference-hardware
  deviation (reference: MacBook Air M1, 8 GB, Chrome; local machine: Mac mini M2, 8 GB, macOS
  26.5.2, Chrome for Testing 156 — recorded as a proxy; the report names what is still unproven).
- Gate documentation: new `docs/gates/perf.md` (command shape, thresholds, hardware rules, exclusive
  resource) and the matching `docs/quality.md` row; `docs/versions.md` gets the Chrome-for-Testing
  row (exact version, source, date, licence) if not already present.
- `.changes/P2-04-perf-baseline.md` (area `engine`, kind `minor`).

## Specifications

- Reference hardware for the target: **MacBook Air M1, 8 GB, Chrome** (owner decision 2026-10-25).
  The local measurement machine is a Mac mini M2, 8 GB, macOS 26.5.2 with Chrome for Testing
  156.0.8078.4; the report must state this deviation explicitly and that the M1 number is still
  unproven until measured on the reference device.
- Frame time: interval between consecutive rAF callbacks while rendering the 50,000-rectangle
  document; discard warm-up samples; report p50/p95/p99 and mean.
- Thresholds: p95 ≤ 16.7 ms (60 fps). Record the renderer backend actually used (ANGLE/Metal,
  SwiftShader) — software rendering is not a valid perf pass; fail with a clear reason instead.
- The gate is exclusive (`exclusive: ["perf"]`): lock it through `gate.py`; never run two
  benchmarks against the same port.
- Browser launch: `--headless=new` if it exposes the real GPU through ANGLE/Metal; otherwise run
  headful in a virtual display-free window and record the flags. Report the flags.
- All commands and their outputs go into the evidence log; the report links the JSON and the log.
- The harness uses the slot's port and stops only the processes it started.

## Pitfalls

- Headless Chromium can silently fall back to SwiftShader; the harness must detect and report the
  renderer (`WEBGL_debug_renderer_info`) and fail a software-rendering result as infra, not pass.
- A cold WASM fetch or shader compile skews the first frames; use the warm-up samples.
- Timing on a busy machine is unstable; the report marks results as proxy evidence when the
  hardware differs from the reference.
- `node` fetch/console plumbing is enough; do not add Puppeteer/Playwright as a dependency.
- `board-check` before any `pnpm` command; if `node_modules/` exists, run check.py before installing.

## Edge cases

- Browser missing → the harness prints the expected path and exits with a clear error, never
  silently skips; the gate fails.
- Page fails to load the WASM → harness fails with the page error, no zero-sample "pass".
- Fewer samples than requested → fail, do not average over too few frames.
- 0 rectangles / 50,000 rectangles / extreme zoom: the report records the primary scenario; the
  others are sanity checks.

## Gates

1. `board-check`: `python3 $POLIER/tools/check.py .` → exit 0 (before any install).
2. `perf-baseline`: `node packages/engine/test/perf/run-perf.mjs` → exit 0, p95 ≤ 16.7 ms at 50,000
   rectangles, JSON evidence written (exclusive).
