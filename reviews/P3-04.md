# Review P3-04 — Platform API routes and api-tests

**Reviewer:** independent subagent · **Date:** 2026-10-25 · **Verdict:** pass

## Acceptance

- **A1: pass** — All 20 contract operations are registered under `/v1` (workspaces, boards, notes, cards × list/create/get/update/delete) with the contract envelopes (`{requestId, items, nextCursor}`, `{requestId, <resource>}`, `{requestId, deletedId}`, flat `{requestId, code, messageKey, details?}`); entity field sets match the workspace/board/note/card schemas, ids are UUIDv7, mutation requestIds are validated and echoed on success, GET takes `?requestId=` with the `x-request-id` fallback, and cursor pagination is opaque base64url over `(created_at, id)` with limit 1–100 and `nextCursor: null` on the last page. Body limits (64 KiB), 415 and 405 map to the nearest contract codes (the same compromise accepted in P3-03 F4); F3/F6/F7 are edge deviations.
- **A2: pass** — The suite proves owner/editor/reader/non-member behaviour (read = member, writes = owner/editor, workspace delete = owner, non-member always 404, note with cards 409); every request runs in one `app_user` transaction with `set_config('app.account_id', …, true)`, only the caller's profile is auto-created, no client-sent account id is trusted (`ownerId` must equal the session), all SQL is parameterized, and note/board `workspace_id` changes are neither accepted nor possible (triggers). F1 is the missing API-level read check and the absent app-role guard.
- **A3: pass** — `node --test services/platform/test/api/*.test.mjs` is 23/23 green (re-run); every one of the 20 routes has an allow and at least one deny case (wrong role, foreign/unknown resource, missing session, invalid payload), the suite resets and migrates the slot database in `before`, closes the platform pool/server and the auth child in `after`, and leaves the DB empty (0 application rows, 3 migrations; verified). F4 (auth child process, not in-process) and F5 (shared fixtures) are the deviations.
- **A4: pass** — All four records are exit 0 / `result: pass`, their `log_sha256` values recompute, they name base `adefe92` with `dirty: true` (normal pre-commit order), the branch has one commit `e739c3d` (38 paths, all inside `services/platform/`, `.changes/` and `reviews/evidence/`), the worktree is clean, and no board/STATUS/CHANGELOG/dependency change exists. I re-ran the service build (exit 0), the unit gate (72/72) and the api-tests (23/23).

## Known follow-ups (judged)

- **(a) v4/v7 account-id gap (F2).** This is the one cross-service issue. Kratos identity ids are UUIDv4 and P3-03 review already recorded that P3-04 must key on `accountId`; P3-04 does, but the id itself is v4. With the current code a real logged-in user cannot create a workspace or board, and any real account-owned workspace would carry a contract-invalid v4 `ownerId`. Severity: **major**, **not a blocker for P3-04** because the brief's acceptance is defined against the v7 test-session path and the root cause lives in P3-02/P3-03 (outside this task's `scope_write`). It **must be a scheduled task before the web stage** (and before the SDK is pointed at real sessions); if the lead treats "a real Kratos session can run the D9 flow end to end" as part of this stage's exit, it becomes a stage blocker. Concrete fix in F2.
- **(b) No member-management routes.** Acceptable for this stage: the P1-05 API contract has no member envelopes and the brief's 20 operations are exactly the four resources. The tests grant editor/reader memberships directly as the owner (documented fixture). A separate task is needed before multi-user web: owner-only invite/list/change-role/remove, plus the same allow/deny tests.
- **(c) GET requestId transport.** `?requestId=` with the `x-request-id` fallback is a reasonable resolution of `docs/contracts.md` open point 1. The contract document still says "decide header or query"; record the chosen transport there before the SDK (lead/contract owner, outside P3-04 scope).
- **(d) Rate limiting.** Not implemented, as the brief allows ("only the error code mapping"); `RATE_LIMITED` exists but is unused. Accept for this stage; expose a limiter before any public deployment.
- **(e) 405/413/415 mapping.** Inherited from P3-03 F4: 405 is returned with `FORBIDDEN`, 413/415 with `VALIDATION`, because the contract has no dedicated codes. Status codes and bodies are consistent; no new finding, but document the compromise for client authors.
- **(f) `.env.example` (F9) and the production `app_user`/SECURITY DEFINER owner** remain lead/next-stage items. The F1 role guard would make the second line fail fast instead of silently trusting the wrong pool.
- **(g) board-check warnings** (STATUS.md length, P3-04 context pack ~128k tokens) are pre-existing board/brief issues, not P3-04 code defects.
