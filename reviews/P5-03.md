## Verdict

The sync service is a real node:http + own RFC 6455 server with the 0.3.0 session protocol: hello
first with version/session, authorized join, durable `operationBatch` (transaction committed before
the ack) and post-ack broadcast, resync catch-up, leave and a presence stub. Fresh boards now have a
contract-valid baseline (`serverSeq` 1) and the join returns the current document; every emitted
message is schema-validated against `sync.schema.json` in the live integration test. Lead re-ran the
sync suite: 12/12 pass (incl. the live socket + slot-PostgreSQL test), and the gates are green.

  the service's pinned `pg`); changes in `services/sync/`, `infra/migrations/`, `docs/realtime.md`,

- **Gates:** board-check `…191323Z`, boundaries `…191323Z`, unit `…191322Z`, db-migrate `…191327Z`
  pass; superseded round-1/2 records removed.
- **Lead verification:** `pnpm --filter ./services/sync test` → 12/12 pass including the live
  integration (real sockets + PostgreSQL).
- **Durability:** append uses a per-board `pg_advisory_xact_lock`, allocates
  `max(max(sync_updates), max(sync_snapshots)) + 1`, inserts, commits, then the protocol acks; an
  append failure maps to a contract reject and no ack.
- **Migration 0006:** `sync_updates` (PK board+serverSeq, encoded update, client/message ids),
  `sync_snapshots` (PK board+serverSeq), catch-up indexes; no parent FK (board access is authorized
  by the platform; documented).
- **Contract:** fresh board = baseline snapshot at 1, first batch = 2, welcome at the current seq,
  outgoing messages validated against the contract schema in the integration test (the earlier
  `serverSeq 0` bug is now impossible to ship).
