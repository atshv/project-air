**Reviewer:** independent subagent · **Date:** 2026-10-25 · **Verdict:** pass

## Acceptance

- **A1: pass** — `kratos.yml` (config version `v26.2.0`, DSN/secrets/cookie flag/SMTP from the environment through Compose, no DSN or generated secret in the tree), `identity.schema.json` (e-mail as password+code identifier with verification/recovery via e-mail, display name 1–80, locale `de`/`en`), Compose `kratos-migrate` (one-shot, `service_completed_successfully`) + `kratos` (`identity` profile, public `/health/ready` health check, admin bound to `127.0.0.1`), and the `tools/dev/setup` secrets (generated once into the gitignored `.env`, mode 600, names only in `.env.example`, never printed) all verify. Live: 338 migrations applied, public/admin health 200, the three self-service flows return 200 with the schema nodes (`traits.email`, `traits.display_name`, `traits.locale`), and Mailpit holds the recovery code e-mail. The host ports `8433/8434` are the P3-01-pinned shared ports and stay outside the slot range 4000–4999, so keeping them instead of the brief's `4433/4434` is acceptable (the container ports remain 4433/4434).
- **A2: pass** — `GET /session` forwards the client Cookie to Kratos `/sessions/whoami`, maps `identity.id`/`traits.email`/`traits.display_name` to `{accountId, email, displayName}`, returns 401 `AUTH_REQUIRED`/`errors.authRequired` without a session and 503 `INTERNAL` when Kratos is unreachable; no account id is read from the request. The live smoke is corroborated by the Kratos access log (cookie/token redacted, whoami 200 with `x-kratos-authenticated-identity-id`, identity `c07b7dcc…`), Mailpit, and an empty identity list after cleanup; the stub suite covers both cases and asserts the exact cookie forwarding.
- **A3: pass** — The HMAC format is `base64url(accountId).base64url(expiry).signature`, compared in constant time, TTL 900 s default / 3600 s maximum; the mode is enabled only with `AUTH_TEST_MODE=1` and refuses `NODE_ENV=production` (start-up exit 2), the route is 404 and the header ignored when off, and `POST /internal/invitations` requires the Bearer admin token, validates `email`/`displayName`/`locale`, maps Kratos 409→`CONFLICT`, 401 without token and 503 when Kratos fails, and ignores any body `accountId`. The re-run suite is 56/56 green and covers tampering, expiry, both session cases, the production refusal and the invitation paths.
- **A4: pass** — Four records (`board-check`, `boundaries`, `unit`, `compose-config`) are exit 0 / `result: pass`, their `log_sha256` values recompute (`e5e36b28…`, `b410e9ac…`, `c9c332bc…`, `d99527f6…`), base `f6deca7` with `dirty: true` (normal pre-commit order). ## Known follow-ups (judged)

- **(a) Kratos admin API has no built-in auth and is bound to 127.0.0.1.** Correct for local development and the admin token only protects our `/internal/invitations` route; the production network/proxy boundary is required and should be written down (F6). Not a blocker for P3-03.
- **(b) Test-session placeholder e-mail/display name.** `testSessionProfile` returns `<accountId>@test-session.project-air.invalid` and `Test session <id>`; P3-04 must key on `accountId` only. The docstring explains this, but the service README does not; acceptable, document it when P3-04 consumes the route.
- **(c) Shared `projectair_kratos` development database.** Documented in `infra/compose/README.md`, `infra/kratos/README.md` and `services/auth/README.md`; tests use the stub Kratos and never depend on it. Acceptable.
- **(d) Kratos left running after the smoke.** It is a machine-wide service and the brief forbids stopping containers; acceptable. The smoke's auth process is no longer listening on 4120 (checked), so no stray service holds the slot port.
- **(e) 24 h non-rotating Kratos sessions (F5).** Recorded for the production decision; not part of the P3-03 acceptance text.
